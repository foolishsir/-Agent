# 评测体系

> RAG 评测的意义不是"证明系统好用"，而是**在改坏的时候能立刻发现**，
> 以及**在犹豫选哪个参数时能拿出依据**。

---

## 一、为什么需要评测

做 RAG 优化时最大的陷阱是"**感觉好像好一点**"。改完 Prompt、调完分块参数、
换个 embedding 模型 —— 每一处都"看起来更合理了"，但没有任何证据。

更糟的是，**没有评测就发现不了回归**：为了让某类问题答得更好而调整参数，
很可能让另一类问题变差，而你在演示时只会挑那几个变好的例子看。

评测解决三件事：

1. **定位瓶颈**：是召回没找到，还是找到了但排序太靠后，还是 LLM 没用对？
   这三种情况的优化方向完全相反。
2. **量化收益**：某个优化到底带来了多少提升，值不值得付那些延迟/成本。
3. **防回归**：改完之后指标有没有掉。

## 二、评测集设计（最关键的一个决策）

### 用「证据文本」标注，不用 chunk id

```jsonl
{"id":"q001","question":"钢刀的更换周期是多久？","reference_answer":"20000 次或 3 个月",
 "evidences":["钢刀的更换周期为 20000 次或 3 个月"],"category":"exact_match","source_pages":[3]}
```

对比两种标注方式：

| | 标注 chunk id | **标注证据文本（本项目）** |
|---|---|---|
| 判断方式 | 直接比对 id | 计算检索结果对证据的覆盖比例 |
| 换分块参数 | ❌ **评测集立刻作废** | ✅ 依然可用 |
| 能支撑参数调优 | ❌ | ✅ |
| 代价 | 精确、判断快 | 需要模糊匹配 |

**这是整个评测体系里最重要的一个决策。** 用 chunk id 标注的评测集
只能验证某一个固定配置，而评测的核心价值恰恰是"比较不同配置"。

匹配算法：归一化（去空白）后先用子串包含快速判断，
不命中时用**最长公共子串**占证据的比例折算（阈值 0.6）。

> 为什么不用字符集合重叠：中文常用汉字就那几百个，
> "这些字都出现过但顺序完全不同"的文本会被判为高匹配，误判率极高。

### 题目分类

| category | 测什么 | 数量 |
|---|---|---|
| `exact_match` | 含型号/数字/日期的精确匹配 | 7 |
| `semantic` | 需要语义理解 | 7 |
| `paraphrase` | **口语化改写**（不照抄文档措辞） | 27 |
| `no_answer` | **文档中无答案，测拒答** | 5 |

### 为什么要专门生成 `paraphrase`

自动生成的问题（"让模型看一个分块，生成它能回答的问题"）有一个致命缺陷：
**它会照抄文档的措辞**。用文档的原话去搜文档，检索必然轻松命中，
指标虚高且毫无区分度。

实测印证了这一点：只跑自动生成题时，**所有检索策略的 Recall@5 都是 1.000**，
消融表里每个阶段的增量都是 0 —— 评测集完全失去了区分能力。

加入口语化改写后（"上百万条、两张表要同步结果数据对不上" 而不是
"百万级双表信息同步数据丢失"），指标才开始有差异。

### 人工复核是必须的

`generate_golden_set.py` 输出的是**候选集**。常见问题：

- 问题依赖上下文（"它是什么？"），单独拿出来无法理解
- 问题里包含了答案（等于泄题）
- 证据被模型"改写"过，不再是原文（匹配会失效）

**全自动生成的评测集会给出虚高的指标，而虚高的指标比没有指标更危险** ——
它会让你基于错误的信息做决策。

## 三、指标

### 检索层（不需要 LLM，快且免费）

| 指标 | 含义 |
|---|---|
| **Recall@K** | 该命中的证据，有多少进了 Top-K |
| **Precision@K** | Top-K 里有多少是真正相关的 |
| **MRR** | 第一个相关结果的排名倒数均值 —— 衡量"排得够不够前" |

> Recall 和 MRR 要一起看。Recall 高但 MRR 低，说明"找得到但排得靠后"，
> 该优化精排；Recall 本身就低，说明"根本没找到"，调精排没有任何意义。

### 拒答层

刻意分成两个**不同**的指标，而不是合成一个"准确率"：

| 指标 | 含义 | 危害 |
|---|---|---|
| **漏答率** | 有答案却拒答 | 体验问题 —— 用户再问一次可能就好 |
| **误答率** | 没答案却硬答 | **正确性问题** —— 用户拿到一个可信的编造内容 |

两者的危害不对等，所以阈值推导时 `false_answer_weight = 2.0`。
这个权重是**产品决策**而不是技术参数，应该由业务方确认。

### 生成层（LLM-as-judge，可选）

| 指标 | 含义 |
|---|---|
| **忠实度** | 回答是否完全由上下文支撑（答对了但资料里没有，也算 0） |
| **正确性** | 与标准答案在事实上是否一致 |

### 延迟

用 **P95** 而不是平均值。平均值会被大量快请求掩盖掉少数慢请求，
而用户记住的恰恰是那几次慢的。

## 四、链路消融：每一阶段贡献了多少

这是评测最有价值的部分之一。它在**同一个配置**下逐阶段观察候选集变化：

```
① 纯向量召回      ← 单路基线
② 纯关键词召回    ← 单路基线
③ +RRF 融合       ← 递进链路从这里开始
④ +父块去重
⑤ +Cross-Encoder 精排
⑥ 最终送入 Prompt(父块)
```

> ⚠️ 前两个是**并列基线**，不是递进链路的环节。
> 把它们当成"RRF 的上一阶段"会得出荒谬的结论
> （比如"BM25 之后 RRF 提升了 0.1"，实际是拿"只用 BM25"当基准）。

---

## 五、怎么跑

```bash
# 1. 生成评测集候选（需要 LLM Key）
python eval/generate_golden_set.py --pdf "你的文档.pdf" \
    --per-chunk 1 --per-chunk-max 8 --paraphrase 2 --no-answer 5 --overwrite
python eval/dedupe_golden_set.py          # 去重
python eval/inspect_golden_set.py         # **人工复核**

# 2. 跑评测
python eval/run_eval.py --pdf "你的文档.pdf" --preset chunk_parent_300
python eval/run_eval.py --pdf "你的文档.pdf" --all          # 全配置对比
python eval/run_eval.py --pdf "你的文档.pdf" --all --with-generation   # 含生成层(会花钱)

# 结果: eval/results/report.md  +  每个配置一个 JSON 明细
```

**工作区是隔离的**：评测使用 `eval/.workspace/` 下独立的 SQLite 与 Chroma 集合，
不会污染开发数据。跑完可以直接删掉整个目录。

评测会**自动继承**你在 Web 界面「设置」里配好的 LLM 参数，不需要重复配置。

## 六、实测结论（简历 PDF，46 条评测集）

### 配置对比

| 配置 | 父块 | 子块 | Recall@5 | MRR | 检索 P95 |
|---|---|---|---|---|---|
| 固定长度（基线） | 3 | 12 | 1.000 | 0.902 | 104 ms |
| 递归字符切分 | 2 | 47 | 1.000 | 0.951 | 78 ms |
| 父子块 child=150 | 7 | 32 | 1.000 | 0.959 | 182 ms |
| **父子块 child=300** | 7 | 16 | 1.000 | **0.988** | 102 ms |
| 父子块 child=500 | 7 | 11 | 1.000 | 0.957 | 130 ms |
| 关闭关键词检索 | 7 | 16 | 1.000 | 0.988 | 77 ms |
| 关闭精排 | 7 | 16 | 1.000 | 0.929 | **13 ms** |

### 消融

| 阶段 | Recall@5 | MRR | 增量 |
|---|---|---|---|
| ① 纯向量召回〔基线〕 | 1.000 | 0.929 | — |
| ② 纯关键词召回〔基线〕 | 0.927 | 0.809 | — |
| ③ +RRF 融合 | 0.951 | 0.909 | — |
| ④ +父块去重 | 0.976 | 0.904 | -0.005 |
| ⑤ +精排 | 0.976 | 0.963 | **+0.059** |
| ⑥ +父块扩展入 Prompt | 1.000 | 0.988 | +0.024 |

### 三条结论（**其中两条与设计假设相反**）

1. **父子块优于基线**：MRR 0.988 vs 固定长度 0.902（**+0.085**）。
   最优子块大小是 300 字（150 → 0.959，300 → 0.988，500 → 0.957）。

2. ⚠️ **RRF 融合在本语料上未带来提升**（0.909 vs 纯向量 0.929）。
   原因：这份文档是简历，几乎没有型号/编号类 token，
   而向量那一路本身已经很强，融合进来的 BM25 结果反而拉低了排名。
   **这不代表混合检索没用** —— 换一份含大量型号的设备手册，结论可能相反。
   → 这正好说明为什么必须按语料做评测，而不是照搬"最佳实践"。

3. ⚠️ **精排分数阈值拒答失效**：无答案题最高分 0.995 ≥ 有答案题最低分 0.002，
   两类**完全重叠**。根因是精排模型判断的是"这段文字与查询是否相关"，
   而不是"这段文字能否回答问题" —— 话题相关但没答案的问题同样拿高分。
   → **需要改为显式的「资料是否足以回答」判定**（先让 LLM 判可用性再生成），
   分数阈值只能作为粗筛。

## 七、已知局限

| 局限 | 影响 | 改进方向 |
|---|---|---|
| 语料只有一份 2 页简历 | 语料太小，很多策略区分不出来（Recall@5 全是 1.000） | 换/加一份几十页的设备手册或规范文档 |
| 评测集 46 条 | 单题权重较大，一个异常样本能明显影响均值 | 扩到 100+ 条，或报告置信区间 |
| 证据匹配是文本相似度 | 语义相同但措辞完全不同的命中会漏判 | 引入 embedding 相似度做二次判定 |
| LLM-as-judge 有偏差 | 评测模型与被评模型同源时有自评倾向 | 换一个厂商的模型做裁判 |
| 单轮评测 | 没有覆盖多轮改写（`multi_turn` 类） | 增加多轮对话评测集 |
| 主语料是中文 | 英文语料上的结论未经验证 | 加英文文档与英文评测集 |

## 八、评测体系自身踩过的坑

评测代码也是代码，同样会出错 —— 而**评测出错的危害更大**：
跑不出来你会立刻发现，算错了却会拿着错误的数字去改代码、写简历。

| 坑 | 现象 | 修法 |
|---|---|---|
| **指标取错层级** | 报告里 `Recall@5 = 0.000` 但 `MRR = 1.000`，自相矛盾 | `recall_at` 是嵌套字典（每个 K 一个值），不能按顶层键取 |
| **短文本误匹配** | "证据甲" 与 "证据乙" 的最长公共子串是 "证据"(2 字)，比例 0.67 超过阈值 → 未命中被算成命中 | 加绝对长度下限 `MIN_MATCH_CHARS = 8` |
| **配置泄漏** | `run_config` 只覆盖自己关心的项、不还原，`pipeline_no_bm25` 设的 `bm25_top_k=0` 泄漏到了下一个配置 —— "关闭精排"的实验实际是"同时关掉关键词检索" | 每个配置运行前先还原基线，并加 `assert_applied` 断言防住"改了没生效" |
| **评级集太简单** | 所有策略的 Recall@5 都是 1.000，消融表每个阶段增量都是 0，完全失去区分度 | 加入口语化改写题（不照抄文档措辞） |
| **P95 的直觉误解** | 100 个样本里 1 个慢请求时 P95 依然"正常" | 这是分位数的数学性质，不是 bug；看尾部要盯 P99 与 max |
| **消融的变量没控制住** | 跨配置平均各阶段指标，把"分块差异"和"链路差异"混在一起 | 只取一个参考配置做消融，并明确标注单路基线不是链路环节 |
