# SKILL 编写规范

> 这个目录存放**项目内置的 SKILL**。前端「面试」页面会扫描本目录，
> 列出所有可用 SKILL 供勾选启用。
>
> 你只需要在这里新建目录 + 写一个 `SKILL.md`，**不需要改任何代码** ——
> 后端启动时自动加载。

---

## 一、目录结构

```
skills/
├── README.md                        本文件
├── technical-interviewer/
│   └── SKILL.md                     ← 一个 SKILL = 一个目录 + 一个 SKILL.md
├── project-deep-dive/
│   └── SKILL.md
└── hr-interviewer/
    └── SKILL.md
```

**目录名用英文小写 + 连字符**，`name` 字段才用中文。

> 为什么不让目录直接用中文名：中文路径在跨平台、打包、命令行里都容易出问题
> （编码、转义、shell 兼容），而项目里其他地方已经为此做过妥协（比如上传文件
> 用 MD5 命名）。展示名放在 front-matter 里，两边都不牺牲。

---

## 二、SKILL.md 的结构

由两部分组成：

````markdown
---
# ---------- 结构化字段：代码会读取，参与状态机判断 ----------
id: technical-interviewer
name: 技术面试官
description: 从简历挑技术点深挖，追问实现细节与技术取舍
icon: 🎯
tags: [技术, 深挖]
max_follow_up: 3        # 同一话题最多追问几层
max_turns: 25           # 整场最多几轮问答
---

# ---------- 正文：会被拼进 Prompt ----------

# 角色
你是一位……

# 提问维度
1. ……

# 追问规则
- ……

# 硬约束
- ……

# 输出格式
……
````

### 为什么要有"结构化字段"这一层

**不能让自然语言定义一切。** 追问深度、最大轮次这类东西必须参与**代码逻辑判断**
（状态机要知道什么时候该停），如果只写在正文里让模型自律，就会出现
"说好最多追问 3 层，实际追问了 7 层把候选人问崩"。

所以：

| 位置 | 谁读 | 用途 |
|---|---|---|
| front-matter | **代码** | 状态机判断、前端展示、参数校验 |
| 正文 | **模型** | 拼进 Prompt，决定提问风格 |

## 三、字段说明

### 必需字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 唯一标识，建议与目录名一致 |
| `name` | string | 展示名，前端勾选框上显示的 |
| `description` | string | 一句话说明，前端鼠标悬浮时显示 |

### 可选字段

| 字段 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `icon` | string | `🎯` | 前端显示的图标（一个 emoji） |
| `tags` | list | `[]` | 标签，用于前端分组或筛选 |
| `max_follow_up` | int | `3` | 同一话题最多追问几层。**超过会强制换话题** |
| `max_turns` | int | `25` | 整场最多几轮问答，防止无限进行 |
| `allow_finish` | bool | `true` | 是否允许模型主动结束面试 |
| `require_evidence` | bool | `true` | 是否校验"问题必须溯源到简历原文" |

> `max_follow_up` 默认 3 是有意的：连续追问超过 3 层，候选人会从"被考察"
> 变成"被折磨"，体验断崖式下跌，而且后面几层的信息量其实很低。

## 四、正文该怎么写

正文会被原样拼进 System Prompt。写的时候记住三条：

### 1. 说清楚「什么情况下该做什么」

不要只写"要深挖"，要写**判断条件**：

```markdown
# 追问规则
- 回答停留在「使用过」层面 → 追问实现原理
- 回答出现具体数字 → 追问测量方法与基线
- 回答提到技术选型 → 追问被放弃的方案与原因
- 回答出现「大概」「应该」「差不多」 → 要求给出具体例子
- 回答正确且具体 → **停止追问，换下一个话题**
```

最后一条很重要：**不要为了难而难**。候选人答得好就该换题，
否则面试变成抬杠，出来的是无效数据。

### 2. 约束要写成硬性规则，而不是建议

```markdown
# 硬约束
- **只能问简历里出现过的内容**，绝不问候选人没写过的东西
- 同一话题连续追问不超过 3 层
- 不给出正确答案（这是面试，不是教学）
- 每次只问**一个**问题
```

### 3. 明确输出格式

模型很容易在问题前面加一堆铺垫（"好的，了解了。那么接下来我想问一下…"），
流式输出时看起来特别啰嗦。

```markdown
# 输出格式
只输出问题本身，不要任何前缀、铺垫或总结。
不要输出「问题：」这样的标签。
```

## 五、多个 SKILL 怎么组合

前端最多勾选 **2 个** SKILL。组合时：

```
最终 System Prompt =
    【首要 SKILL】的正文
  + 【次要 SKILL】的正文（作为补充视角）
  + 简历全文
  + 面试状态（提纲 / 已问过的 / 当前追问层级）
```

**结构化字段取"更严格的一方"**：

| 字段 | 组合规则 | 理由 |
|---|---|---|
| `max_follow_up` | 取 `min` | 更严格的限制优先，避免组合后失控 |
| `max_turns` | 取 `min` | 同上 |
| `require_evidence` | 任一为 true 则 true | 安全约束只增不减 |

> 这个规则和"限流参数取最小值""权限取交集"是同一个思路：
> **安全相关的约束在组合时只能更严，不能更松。**

## 六、新增 SKILL 的步骤

1. 在 `skills/` 下新建英文小写目录，例如 `skills/stress-interviewer/`
2. 在里面创建 `SKILL.md`，按上面的格式填写
3. **重启服务**（或调用 `POST /api/v1/skills/reload` 热加载）
4. 打开前端「面试」页面，新 SKILL 会出现在勾选列表里

**不需要改任何代码** —— 加载器是扫描目录的。

---

## 七、调试建议

写完 SKILL 后，最有用的验证方式是**看前三个问题**：

```bash
python scripts/test_skill.py --skill technical-interviewer \
    --resume samples/你的简历.pdf --rounds 3
```

如果前三个问题里有任何一个让你觉得"这个问题没内味"，那就是正文写得不够具体。

**常见问题**：

| 现象 | 原因 | 修法 |
|---|---|---|
| 问题很泛（"介绍一下你的项目"） | 提问维度没写清楚 | 补上具体的切入角度 |
| 问了简历里没有的东西 | 硬约束不够强 | 加"只能问简历里出现过的内容"，并确认 `require_evidence: true` |
| 不停追问同一个点 | `max_follow_up` 太大或追问规则没写"答好了就换" | 补上停止条件 |
| 问题前有一堆铺垫 | 输出格式没约束 | 明确写"只输出问题本身" |
