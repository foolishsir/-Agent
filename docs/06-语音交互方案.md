# 语音交互方案（ASR + TTS）

> 本文是**设计预研**，不是已实现的功能。目的是在动手前把技术选型、
> 真正的难点、延迟预算和实现路径讲清楚，避免做到一半发现方案不成立。

---

## 一、结论先行

| 问题 | 回答 |
|---|---|
| 能不能做 | **能**，且不需要推翻现有架构 |
| 难度在哪 | 不在"调 API"，而在**流式合成的时序控制**和**打断机制** |
| 最契合的现有设计 | **SSE token 流** —— 句子级流式 TTS 直接挂在它上面 |
| 预期工作量 | V1 快速版 1 天；可写进简历的完整版 5~7 天 |
| 我的建议 | **先做评测（P5），再做语音**。理由见文末 |

**一句话架构**：

```
麦克风 → VAD → ASR → [现有 RAG 链路] → token 流
                                          ↓
                                   句子缓冲（遇 。！？ 就切）
                                          ↓
                                      TTS 合成
                                          ↓
                                     音频队列 → 播放
```

中间那段 `[现有 RAG 链路]` **一行都不用改**。语音只是换了输入输出的形态。

## 二、语音输入（ASR）选型

| 方案 | 部署 | 中文效果 | 延迟 | 成本 | 评价 |
|---|---|---|---|---|---|
| **Web Speech API** | 浏览器内置 | 一般 | 低 | 免费 | Chrome 专属、部分实现要联网。**适合 V1 快速验证交互** |
| **faster-whisper** | 本地 GPU | 好 | 中 | 免费 | **推荐**。你有 RTX 4060，small/medium 模型够用，数据不出域 |
| Whisper API | 云端 | 好 | 中 | 便宜 | 省事，但音频要上传（隐私场景不可接受） |
| 讯飞 / 阿里实时 ASR | 云端 WebSocket | 最好 | 低 | 按量计费 | 追求"边说边出字"的体验时选它 |

**推荐组合**：`faster-whisper`（本地）为主，`Web Speech API` 作为零部署降级路径。

> **为什么本地 Whisper 是加分项而不只是省钱**：
> 这个项目一直在强调"私有文档不出域"。如果 ASR 走云端，音频（也就是**文档内容的口述版**）
> 就出境了，前面的隔离设计全白做。本地 ASR 让"数据不出域"这条线是完整的 ——
> 这是面试时能主动讲的一个架构一致性论点。

### 关键工程问题

**① 音频格式转换**
浏览器 `MediaRecorder` 给出的是 **WebM/Opus**，而 Whisper 要 **16kHz 单声道 PCM**。
`faster-whisper` 内部用 PyAV 解码，但依赖 ffmpeg 二进制 —— 这在 Windows 上是个部署坑。
两个选择：

- 打包 ffmpeg（镜像体积 +70MB，但省事）
- 前端用 `AudioWorklet` 自己重采样成 16kHz PCM 裸流再上传（无依赖，但代码量增加）

**② 分片 vs 整段**
- **整段识别**（用户说完再传）：实现简单，延迟 = 说话时长 + 识别时间
- **流式识别**（边说边传）：体验好，但需要 VAD 切分 + 增量解码，复杂度显著上升

建议 V2 先做整段，V3 再考虑流式。

## 三、语音回复（TTS）选型

| 方案 | 部署 | 音质 | 延迟 | 成本 | 评价 |
|---|---|---|---|---|---|
| **SpeechSynthesis** | 浏览器内置 | 差（机械感重） | 极低 | 免费 | 零成本兜底，**首字延迟几乎为 0** |
| **edge-tts** | 需联网 | **很好** | 低 | **免费** | 用的是微软在线音色，性价比极高 |
| OpenAI TTS | 云端 | 很好 | 中 | 按量 | 音色统一、多语言好 |
| CosyVoice / ChatTTS | 本地 GPU | 好 | 中 | 免费 | 完全离线，但 8G 显存跑起来吃力 |
| GPT-SoVITS | 本地 GPU | 可克隆音色 | 中 | 免费 | 想做"自己的声音"时选它 |

**推荐组合**：`edge-tts` 为主（免费且音质好），`SpeechSynthesis` 作为离线降级。

## 四、四个真正的难点

### 难点 1：流式 TTS 的句子缓冲（**核心难点**）

**错误做法**：等 LLM 把整段回答生成完，再一次性合成。

后果：用户要等**整个回答生成完 + 合成完**才听到第一声。
一段 800 字的回答生成要 10 秒，用户就一直干等 —— 语音交互的体验直接崩掉。

**正确做法**：在 token 流上做**句子级切分**，边生成边合成边播放。

```python
buffer = ""
async for token in llm.astream(...):
    buffer += token
    # 双阈值：要么攒够一个完整句子，要么等太久了也要吐出去
    if 遇到句末标点(buffer) and len(buffer) >= MIN_SENTENCE:
        yield buffer; buffer = ""
    elif 已等待 > MAX_WAIT_MS:
        yield buffer; buffer = ""
```

**双阈值策略是必需的**，缺一不可：

- 只看句末标点 → 遇到"好的。"这种极短句，会合成出一堆碎片音频，听起来一顿一顿的
- 只看长度 → 一句话从中间切断，语调会很怪
- **最小句长 + 最大等待时间**同时约束，才能兼顾流畅度与延迟

**还要处理**：LLM 偶尔会输出超长的不带标点的句子（比如一长串型号），
必须有硬上限兜底，否则缓冲永远不 flush。

### 难点 2：朗读前必须"文本口语化"（**最容易漏**）

答案里的这些内容**直接读出来是灾难**：

| 内容 | 直接读会变成 |
|---|---|
| `[1]` 引用角标 | "左方括号一右方括号" |
| `**AI 应用**` | "星号星号 AI 应用 星号星号" |
| `- Java` | "减号 Java" |
| Markdown 表格 | 逐格念出来完全无法理解 |
| `20000` | 需要读成"两万"而不是"二零零零零" |
| 代码块 | 逐字符念出来毫无意义 |

**关键洞察**：这和屏幕渲染是**同一份数据的两种输出形态**。

你刚做完的 Markdown 渲染是"给眼睛看的"，TTS 需要的是"给耳朵听的"。
两者应该共用同一个规范化管道的**上游**（引用校验后的 `cleaned_answer`），
然后分两条支路：

```
                    ┌─→ Markdown 渲染 → 屏幕
cleaned_answer ─────┤
                    └─→ 口语化转换 → TTS → 扬声器
```

建议把"口语化转换"做成独立模块（`services/speech/normalizer.py`），
这样它可单独测试，也能被将来任何"文本转语音"的需求复用。

**具体要做的转换**：

- 剥离引用角标、Markdown 标记、代码块（或替换为"以下省略一段代码"）
- 表格转成"参数 A 是 1，参数 B 是 2"这样的并列句
- 数字/单位口语化（`20000 次` → `两万次`）
- 中英混排的停顿处理

### 难点 3：打断（Barge-in）

用户听到一半想插话，必须立刻：**停止播放 → 取消 LLM 流 → 清空音频队列**。

这需要一条**取消链路**贯穿前后端：

```
前端 VAD 检测到人声
   → abort() 掉 fetch(SSE 连接断开)
   → 后端感知断开 → 取消 LLM 请求（省 token 也省算力）
   → 清空本地音频缓冲 → 停止播放
```

**坑点**：HTTP 连接断开后，服务端**不一定立刻知道**。
Starlette 提供了 `await request.is_disconnected()`，但需要轮询；
`asyncio.CancelledError` 的传播时机也依赖具体实现。
这块要做实测，不能想当然。

> **面试价值**：这是一个典型的**分布式取消传播**问题 ——
> 和"用户关掉页面后后端还在跑一个耗时的批处理"是同一类问题。
> 能把这条链路的每一环讲清楚，比"我接了个 ASR API"有含量得多。

### 难点 4：回声消除

用外放 + 麦克风时，**TTS 播出来的声音会被麦克风录进去**，ASR 会把助手自己的话
当成用户输入 —— 表现是"助手自己跟自己说话"。

- 浏览器层面：`getUserMedia({ audio: { echoCancellation: true, noiseSuppression: true } })`
- 但**外放场景下 AEC 效果有限**，工程上更可靠的做法是**半双工**：
  播放时暂停录音，或用 VAD 做简单的"谁在说话"仲裁

## 五、延迟预算

语音交互的体验几乎完全由**首字延迟**决定（用户说完 → 听到第一声）。

| 环节 | 耗时 | 备注 |
|---|---|---|
| ASR（整段 5 秒语音） | 300~1000 ms | 本地 whisper-small on GPU |
| 检索（向量 + BM25 + RRF + 精排） | 300~800 ms | 已有实测数据 |
| LLM 首 token | 500~1500 ms | **最大头**，取决于服务商 |
| 首句 TTS 合成 | 200~500 ms | edge-tts |
| **合计** | **1.3~3.8 s** | |

**优化手段**：

1. **填补等待**：检索一开始就播一句"正在查找…"（预合成的固定音频，延迟 0）
2. **降低首句阈值**：第一句话用更小的 `MIN_SENTENCE`，让用户尽快听到声音
3. **提前触发**：ASR 出中间结果时就开始检索（流式 ASR 才有这个能力）
4. **并行**：TTS 合成与 LLM 生成并行（本身就是流式管道，天然并行）

## 六、实现路线图

| 阶段 | 内容 | 产出 | 工作量 |
|---|---|---|---|
| **S1** | 前端 `SpeechRecognition` + `SpeechSynthesis` | 能语音问、语音答 | 1 天 |
| **S2** | 后端 `faster-whisper` + `edge-tts`，新增 `/speech/transcribe` 与 `/speech/synthesize` | 私有化语音链路 | 2 天 |
| **S3** | 口语化转换模块 + 单元测试 | 不再读出星号和方括号 | 1 天 |
| **S4** | **句子级流式 TTS**（挂在现有 SSE 上） | 首字延迟从 10s 降到 1.5s | 2~3 天 |
| **S5** | VAD 打断 + 取消链路 | 能插话 | 1~2 天 |
| **S6** | WebSocket 双向通道（替代 SSE） | 全双工、支持流式 ASR | 2~3 天 |

**建议做到 S4 就够了** —— S5/S6 是体验打磨，投入产出比明显下降。

## 七、简历与面试怎么包装

**能写的量化指标**（都是可测的）：

> - 实现端到端语音问答：本地 `faster-whisper` 做 ASR，全链路**音频不出域**
> - 自研**句子级流式 TTS 管道**，把首字延迟从 X 秒降到 Y 秒
> - 基于 VAD 实现**说话打断**，联动取消 LLM 流式生成，节省 Z% 的 token 消耗

**面试能展开的三个点**：

1. **"为什么不用现成的语音 SDK？"**
   → 因为流式时序控制（句子缓冲的双阈值）没有现成方案，必须自己做；
   而且 SDK 通常是"整段进整段出"，与我们的 token 流对不上。

2. **"为什么 ASR 要本地部署？"**
   → 架构一致性。项目承诺文档不出域，如果 ASR 走云端，
   音频（文档内容的口述版）就出境了，前面的隔离设计全部失效。

3. **"打断怎么实现的？"**
   → 讲完整的取消链路：前端 abort → 连接断开 → 服务端 `is_disconnected()`
   → 取消 LLM 请求 → 释放算力。顺带说明"断开检测不是即时的"这个工程细节。

## 八、我的建议

**先做 P5 评测体系，再做语音。** 三个理由：

1. **面试官更可能问"你怎么知道你的 RAG 效果好"，而不是"你能不能说话"**
   —— 评测是技术深度，语音是功能广度
2. **语音是锦上添花，评测是地基**。检索质量不行的话，语音只会让"答错"这件事
   传播得更快（用户听着一个自信的男声念出错误答案）
3. 你已经有的分块调参功能**急需评测来闭环** —— 现在能调参，但没法量化哪种参数更好

**但如果**你投的是**多模态 / 语音交互 / AI 应用**方向，语音的差异化价值会显著上升，
那时可以把它提到 P5 之前。

**最优顺序**：P5 评测 → P4 异步队列 → P6 Vue3 前端 → 语音（S1~S4）。
