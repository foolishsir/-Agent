# 面试官 Agent 方案

> 本文是**设计预研 + 已确认的决策**。SKILL 的编写规范见
> [`skills/README.md`](../skills/README.md)，本文件讲的是系统怎么运转。

---

## 一、这不是 RAG 问答的变体

先认清一件事：**交互范式变了**。

| | 现有系统（问答） | 面试官 Agent |
|---|---|---|
| 谁主动 | **用户**提问 | **Agent** 提问 |
| 输入 | 用户的问题 | 简历 + 上一轮的回答 |
| 输出 | 答案 | 下一个问题 |
| 状态 | 基本无状态 | **强状态**：提纲、追问层级、轮次 |
| 循环 | 一次检索 + 生成 | **评估 → 决策 → 再提问** |

现有链路是 `检索 → 生成答案`，是一条直线。新链路是一个**闭环**：

```
加载 SKILL + 简历
      ↓
  规划面试提纲
      ↓
  ┌──→ 提问 ──→ 等待回答 ──→ 评估回答质量 ──┐
  │                              ↓          │
  │                         决策：          │
  │                    ┌──── 值得深挖 → 追问 ┘
  │                    └──── 够了 → 下一个话题 ┘
  └────────────────────────────────────────┘
      ↓
  生成面试报告
```

**关键区别**：追问不是预设的，而是**基于回答质量的动态决策**。
这是它与"提前写好一串问题逐个问"的本质不同。

## 二、SKILL 机制（已确认）

### 定位

**项目内置，不进数据库，不支持用户在网页上编写。**

```
skills/
├── README.md                    编写规范
├── technical-interviewer/SKILL.md
└── project-deep-dive/SKILL.md
```

后端启动时**扫描目录**加载，新增 SKILL 不需要改任何代码。

### SKILL 的两层结构

```markdown
---
id: technical-interviewer       ← 结构化字段：**代码读取**
name: 技术面试官
max_follow_up: 3
max_turns: 25
require_evidence: true
---

# 角色                         ← 正文：**模型读取**（拼进 Prompt）
你是一位……
```

**为什么要分两层 —— 不能让自然语言定义一切。**

`max_follow_up` 这类参数必须参与**代码逻辑判断**（状态机要知道什么时候强制换话题）。
如果只写在正文里让模型自律，就会出现"说好最多追问 3 层，实际追问了 7 层
把候选人问崩"。**约束必须由代码执行，不能指望模型自觉。**

> 这和项目里已有的设计是同一个思路：Prompt 只能缓解，代码才能兜住
> （引用编号校验、拒答阈值都是这个模式）。

### 前端勾选启用

- 「面试」页面列出所有可用 SKILL（`id` 隐藏，展示 `name` + `icon` + `description`）
- **最多勾选 2 个**
- 组合规则见下

### 多 SKILL 组合

```
System Prompt = 【首要 SKILL 正文】+ 【次要 SKILL 正文(补充视角)】
                + 简历全文 + 面试状态
```

结构化字段取**更严格的一方**：

| 字段 | 规则 | 理由 |
|---|---|---|
| `max_follow_up` | `min` | 更严格的限制优先 |
| `max_turns` | `min` | 同上 |
| `require_evidence` | 任一为 true 则 true | 安全约束只增不减 |

> 与"限流取最小值""权限取交集"同一个思路：**安全相关的约束组合时只能更严。**

## 三、核心决策：简历走**全量注入**，不走检索

这是整个方案里最重要的一个技术选择。

| | 走检索（复用现有 RAG） | **全量注入** |
|---|---|---|
| 做法 | 检索相关片段再喂 | 整份简历塞进 Prompt |
| 优点 | 支持超长文档、省 token | 面试官有**全局视角** |
| 缺点 | **只有局部视角** | 简历太长会超上下文 |

### 为什么面试官必须看全文

1. **发现矛盾** —— 实习 A 写"负责后端"，项目 B 又写"独立完成全栈"。
   这种矛盾只有通读全文才能发现，Top-K 检索永远看不出来。
2. **判断经历连贯性** —— 技术栈演进路径、跳槽节奏。
3. **选择切入点** —— 需要先有全貌，才能规划出合理的提问顺序。

### 规模问题与混合策略

简历通常 2~3 页（几千字），全量注入完全没问题。

**但如果用户上传的是几十页的作品集**，就要走混合策略：

```
简历摘要（全量，压缩后） + 检索到的细节（按需）
```

摘要负责"全局视角"，检索负责"具体细节"。

> **面试怎么讲**：
> "我把简历从检索链路上摘出来了，改成全量注入。因为面试官需要的是
> 全局视角 —— 发现经历之间的矛盾、判断技术栈演进，这些靠 Top-K 做不到。
> 检索擅长'找到相关片段'，而面试需要的是'理解整份文档'。
> **同一份文档，不同的任务需要不同的注入方式。**"

## 四、防幻觉：问题必须溯源到简历

这是体验上最容易翻车的地方。

**如果面试官问"你在 XX 公司做的那个推荐系统…"，而简历里根本没写过**，
候选人会直接懵掉，对系统的信任感瞬间归零。

沿用项目里已经验证过的**两层防线**：

```
① Prompt 层：SKILL 的硬约束里写明"只能问简历里出现过的内容"
② 服务端校验：问题生成后，提取其中的关键实体
             （公司名 / 技术名词 / 项目名 / 数字）
             → 逐个检查是否出现在简历原文中
             → 不在 → 重生一次
             → 再不行 → 换话题，跳过这个点
```

**这是"引用编号校验"的同一种模式**：Prompt 只能缓解，服务端才能兜住。

`require_evidence: true` 的 SKILL 才启用这层校验（默认开启）。

## 五、面试状态机

### 数据模型

```
InterviewSession
├── id / user_id / doc_id
├── skill_ids: ["technical-interviewer", "project-deep-dive"]
├── plan: JSON          面试提纲（开始时生成一次）
├── status: PLANNING | IN_PROGRESS | FINISHED
├── turn_count: int
└── created_at / finished_at

InterviewTurn                    每轮一条
├── question: str
├── answer: str
├── evaluation: JSON     { 技术深度, 具体性, 量化意识, 亮点, 疑点 }
├── decision: str        FOLLOW_UP | NEXT_TOPIC | FINISH
├── follow_up_depth: int 当前话题的追问层级
└── created_at
```

### 两个字段值得单独说

**`plan`（面试提纲）** —— 开场时由 LLM 通读简历生成一次，形如：

```json
[
  {"topic": "1333 机种全栈开发", "angle": "量化结果来源", "question": "..."},
  {"topic": "Redis 分布式锁", "angle": "实现深度", "question": "..."},
  ...
]
```

后续每轮**从提纲里取下一个待问点**，或对当前点追问。
这样面试是**有主线的**，而不是每轮临时想一个话题。

**`decision`（决策）落库** —— 两个作用：一是能回放"为什么这里追问了"，
二是调 Prompt 时可以统计"追问率是不是太高"。

### 决策逻辑（代码层，不完全交给模型）

```
每轮回答后：
  ① 让模型评估回答质量，输出结构化 JSON
  ② 代码根据评估结果 + 状态决定：
       - follow_up_depth >= max_follow_up  → 强制 NEXT_TOPIC
       - 评估显示"具体/有细节/有取舍"       → NEXT_TOPIC
       - 评估显示"含糊/停留在使用层面"      → FOLLOW_UP，depth += 1
       - 提纲问完 且 turn_count 到阈值      → FINISH
```

**关键**：模型只负责"评估质量"，**是否追问由代码决定**。
把决策权放在代码里，才能保证 `max_follow_up` 这类约束真的生效。

## 六、模块划分

```
backend/app/services/skills/
├── base.py        Skill 数据模型 + Markdown front-matter 解析
├── registry.py    扫描 skills/ 目录、加载、校验、热重载
└── composer.py    多 SKILL 组合（正文拼接 + 结构化字段取最严）

backend/app/services/interview/
├── planner.py     简历 → 面试提纲
├── evaluator.py   回答 → 结构化评估
├── conductor.py   主循环状态机（评估 → 决策 → 提问）
├── verifier.py    问题溯源校验（关键实体是否在简历里）
└── reporter.py    面试报告（评分 + 薄弱点 + 建议）

backend/app/api/v1/
├── skills.py      GET /skills 列出可用 SKILL（供前端勾选）
│                  POST /skills/reload 热重载目录
└── interview.py   POST /interview/start / answer / finish
                   GET  /interview/{id} 面试记录
```

**复用的现有资产**：

| 现有模块 | 复用方式 |
|---|---|
| 文档上传 / 解析 / 分块 | 简历入库直接用 |
| `Conversation` / `Message` 表 | 加 `mode` 字段区分问答与面试 |
| LLM 客户端（流式 + 非流式） | 直接复用 |
| SSE 流式输出 | 面试官提问也流式输出 |
| 引用校验模式 | 复用到"问题必须来自简历"的校验 |
| 会话侧边栏 | 面试记录也进侧边栏 |

## 七、分阶段实现

| 阶段 | 内容 | 验收标准 | 工作量 |
|---|---|---|---|
| **I1** ✅ | SKILL 加载 + `GET /skills` + 前端勾选框 + **单轮提问** | 勾选 SKILL 后，能基于简历生成第一个像样的面试问题 | 1~2 天 |
| **I2** ✅ | **追问决策循环** + 提纲规划 + 问题溯源校验 | 连续 5 轮，追问是"跟着回答走"的而不是预设的 | 2~3 天 |
| **I3** | 面试会话持久化 | 刷新页面能接着面 | 2 天 |
| **I4** ✅ | 面试报告（评分 + 薄弱点 + 改进建议） | 面完能拿到一份可读的报告 | 1 天 |
| **I5** | 多 SKILL 组合调优 | 组合出的面试风格能明显区分 | 1 天 |

> I1 / I2 / I4 一次做完（前端界面一并在内），I3 单独留待后续 ——
> 面试状态目前由**前端持有并每次回传**，这样 I1~I2 不用先加一张面试表，
> 调试时也能直接在请求体里看到完整状态。

### 实现与原方案的偏差（都是刻意的）

| 原方案 | 实际实现 | 原因 |
|---|---|---|
| 面试状态存库 | **前端回传** | 数据量小（提纲 + 十几轮），回传成本可忽略；I3 再落库 |
| 问题溯源做**硬校验**（不合格丢弃） | **只做标记**（前端标黄） | 简历写"缓存中间件"、问题问"Redis"可能是合理具体化，直接丢弃会误伤 |
| 溯源校验查中文词 | **只查高信号词**（拉丁字母 + 带符号） | 中文常用词遍地都是，查了全是噪声；**宁可漏报也不误报** |
| 评估结果含分数，直接喂模型 | **只传结论不传分数** | 把 `0.37` 丢给模型，它会过度解读 |

### I1 的验收结果

按原定标准验的是"第一个问题像不像真人面试官"，不是"接口通不通"。
实际跑下来（见 `backend/scripts/smoke_interview.py`），提纲规划能正确
挑出简历里**值得追问**的点，而不是"介绍一下你的项目"这类泛泛问题 ——
说明 SKILL 正文的提问维度写到位了。

**但也发现一个真实的坑**：DeepSeek 的 Key 过期时，`/health/ready` 依然报
`llm: ready`（它只检查"配没配"，不检查"能不能用"）。要真正验证 Key 是否可用，
得走「设置」页的**测试连接**按钮 —— 那里是真的调一次模型。
这算是健康探针的一个已知盲区。

### I1 是最关键的验证点

**I1 不是为了"能跑"，而是为了验证 SKILL 的 Prompt 写得对不对。**

如果前三个问题里任何一个让人觉得"没内味"（比如问出"介绍一下你的项目"
这种泛泛的问题），那说明 SKILL 正文的**提问维度写得不够具体**，
得先调那个 —— 而不是急着做追问逻辑。

因为 I2 的追问是建立在 I1 的问题质量之上的：
**问题本身就没深度，追问只会把没深度的问题问三遍。**

## 八、面试价值

做完之后可以这样讲：

> "我基于现有 RAG 系统做了一个面试官 Agent。它不是 RAG 的变体 ——
> RAG 是'用户问、系统答'，这个是'Agent 主动问、评估回答、决定是否追问'，
> 是个**有状态的多轮循环**。
>
> 三个设计点我比较满意：
>
> 一是**简历改成了全量注入**。面试官需要全局视角来发现经历之间的矛盾，
> 这是 Top-K 检索做不到的 —— 检索擅长找片段，面试需要理解整份文档。
>
> 二是**追问是基于回答质量的动态决策**，不是预设脚本。而且**决策权在代码里**，
> 模型只负责评估质量。因为 `max_follow_up` 这类约束如果交给模型自律，
> 它一定会超 —— 这和我在引用校验里踩过的坑是同一个道理。
>
> 三是**问题必须溯源到简历原文**，沿用了我做引用校验的思路：
> Prompt 只能缓解，服务端校验才能兜住。面试官问出简历里没有的东西，
> 候选人对系统的信任会瞬间归零。
>
> 另外我把 SKILL 做成了**目录扫描 + front-matter 结构化字段**的形式。
> 新增一个面试风格只需要写一个 Markdown 文件，不用改代码；
> 而追问深度这种要参与状态机判断的参数，放在结构化字段里由代码读取，
> 不是写进 Prompt 里让模型自己数。"
