## 一、先建立心智模型：一次请求的生命周期

**这是整份文档最重要的一节。** 把这 8 步背下来，P0 的代码你就串起来了。

```
客户端 GET /api/v1/health  (带 X-Trace-Id: abc123)
   │
   │ ① 进程启动时已经做完的事：
   │    lifespan 启动钩子 → setup_logging() → settings.ensure_dirs()
   │
   ▼
② TraceIdMiddleware.dispatch()
   │  - 从请求头读 X-Trace-Id，没有就生成一个 12 位随机串
   │  - set_trace_id() 写进 ContextVar  ← 这一步是后面所有日志能串起来的关键
   │  - 记下开始时间（性能计时）
   ▼
③ 路由匹配 → app.include_router(api_router, prefix="/api/v1")
   │  实际命中 api/v1/health.py 的 liveness()
   ▼
④ 接口函数执行
   │  - 正常返回 → ok(data) 组装成 {code, message, data, trace_id}
   │  - 抛 AppException → 被 @app.exception_handler(AppException) 接住
   │  - 抛其他异常    → 被 @app.exception_handler(Exception) 接住
   ▼
⑤ Middleware 的 finally 块
   │  - 算出耗时
   │  - 写访问日志（超 3 秒降级为 WARNING）
   │  - 把 trace_id 写回响应头 X-Trace-Id
   ▼
⑥ 返回 JSON
```

**关键理解**：`TraceIdMiddleware` 是**包裹**在整个请求外面的，
异常处理器是在**中间**执行的。所以即使接口抛异常，中间件的 `finally` 依然会记录日志 ——
这就是为什么访问日志能记到 500 的请求。

```python
# middleware.py 的核心结构
try:
    response = await call_next(request)   # ← 异常处理器在这一步内部执行
    return response
finally:
    # 无论成功还是抛异常，这里都会执行
    logger.info("... cost_ms=%.1f ...", elapsed_ms)
```

> **面试怎么讲**：
> "我把 trace_id 放在 ContextVar 而不是全局变量，是因为 asyncio 下多个请求是并发交织执行的，
> 用全局变量会让不同请求的 id 互相覆盖。ContextVar 是按协程隔离的，天然不会有这个问题。"

## 二、core/config.py —— 配置中心

### 它做什么

把散落在各处的配置项集中成一个**强类型对象**，且支持环境变量 / `.env` 覆盖。

### 关键代码逐段拆解

#### ① 项目根目录的推导

```python
# backend/app/core/config.py -> docmind/
PROJECT_ROOT: Path = Path(__file__).resolve().parents[3]
```

`parents[0]` = `core/`，`parents[1]` = `app/`，`parents[2]` = `backend/`，`parents[3]` = `docmind/`。

**为什么不用 `os.getcwd()`**：工作目录取决于你从哪里启动服务。
从 `docmind/` 启动和从 `docmind/backend/` 启动，`cwd` 不同，
导致 `data/` 会落在两个不同的地方。用 `__file__` 推导则**永远指向同一个位置**。

> 这是一个非常经典的坑：本地开发时数据都在，一部署到 systemd/Docker 里数据就"丢了"，
> 其实就是 cwd 变了。

#### ② 把 .env 灌进 os.environ

```python
load_dotenv(ENV_FILE, override=False)
```

**为什么 pydantic-settings 已经读 .env 了，还要再手动 load 一次？**

因为**第三方库不走 pydantic-settings**。最典型的就是 `HF_ENDPOINT` ——
它由 `huggingface_hub` 直接读 `os.environ`。如果不手动灌，就会出现
"`.env` 里明明配了镜像，下载模型还是超时"这种极难排查的问题。

`override=False` 保证：真实的系统环境变量 > `.env` 文件。
这样容器部署时用 `docker run -e` 覆盖配置才能生效。

> **面试怎么讲**：
> "我在这里踩过一个坑：pydantic-settings 只负责它自己声明的字段，
> 第三方库读的环境变量它管不着。所以我在配置模块里显式 load_dotenv 一次，
> 并且用 override=False 保证容器注入的环境变量优先级更高。"

#### ③ 环境变量前缀隔离

```python
model_config = SettingsConfigDict(
    env_prefix="DOCMIND_",
    case_sensitive=False,
    extra="ignore",
)
```

**为什么一定要加前缀**：字段名叫 `debug`、`port`、`host`，
如果不加前缀，系统里任何一个叫 `DEBUG` 或 `PORT` 的环境变量都会污染你的配置 ——
这可能来自你装过的某个软件、某个 IDE、某个 CI 系统。加上 `DOCMIND_` 前缀彻底隔离。

`extra="ignore"` 的作用：`.env` 里存在但 Settings 未声明的变量（比如 `HF_ENDPOINT`）
不会导致报错。默认行为是 `forbid`（报错）或 `ignore`，这里显式声明意图。

#### ④ 列表字段的坑（本项目真实踩到）

```python
cors_origins: Annotated[list[str], NoDecode] = Field(default_factory=[...])
```

**不加 `NoDecode` 会怎样**：直接抛

```
SettingsError: error parsing value for field "cors_origins" from source "EnvSettingsSource"
```

**根因**：`pydantic-settings` 对 `list` / `dict` 这类复杂类型，
会**在校验器（field_validator）执行之前**先尝试 `json.loads()` 解码环境变量的值。
所以 `.env` 里写：

```bash
DOCMIND_CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
```

它先试图 JSON 解析 → 失败 → 直接抛 `SettingsError`，
你写的 `field_validator` **根本没机会执行**。

**解法**：`NoDecode` 注解关掉自动解码，改由自己的校验器处理。

```python
@field_validator("cors_origins", mode="before")
@classmethod
def _normalize_origins(cls, v: object) -> object:
    if isinstance(v, str):
        return [item.strip() for item in v.split(",") if item.strip()]
    return v
```

`mode="before"` 表示**在校验之前**处理原始值，这是能把 `str` 转成 `list` 的关键。

> **面试怎么讲**（这是可以主动抛出来的加分点）：
> "我遇到一个 pydantic-settings 的隐式行为：它对 list/dict 类型会先做 JSON 解码，
> 优先级高于字段校验器。所以逗号分隔这种更符合直觉的配置写法会直接报错，
> 而且报错发生在你的校验逻辑之前，很难定位。我用 `NoDecode` 注解关掉自动解码解决了。
> 这件事让我意识到**配置层也必须写单元测试** —— 因为出错时机太早，不测就发现不了。"

#### ⑤ 路径统一解析

```python
@model_validator(mode="after")
def _resolve_paths(self) -> Settings:
    for name in ("data_dir", "upload_dir", "log_dir", "chroma_persist_dir"):
        raw: Path = getattr(self, name)
        if not raw.is_absolute():
            raw = PROJECT_ROOT / raw
        setattr(self, name, raw.resolve())
    return self
```

`mode="after"` 表示在字段都校验完之后执行。
`.env` 里写的是相对路径 `data/chroma`（人类可读、可移植），
但程序内部统一用绝对路径（不受 cwd 影响）。

> **注意**：这里用了 `setattr`，所以**不能**给模型加 `frozen=True`（会抛异常）。
> 生产项目里如果开了 `validate_assignment=True`，这里会触发重复校验，
> 需要改成用 `model_copy(update=...)` 构造新对象。这是一个隐藏的耦合点。

#### ⑥ 单例缓存

```python
@lru_cache(maxsize=1)
def get_settings() -> Settings:
    return Settings()

settings: Settings = get_settings()
```

**为什么必须缓存**：`Settings()` 每次实例化都要读文件、解析、校验。
如果每个请求都调用一次，就是纯粹的浪费。`lru_cache` 让整个进程只解析一次。

**为什么同时提供模块级 `settings` 变量**：方便 `from app.core.config import settings` 直接用，
省去每次调用函数。代价是**测试时不好替换** —— 所以测试里是通过环境变量而不是 mock 来隔离的。

## 三、core/logging.py —— 全链路日志

### 它做什么

1. 给每条日志自动带上**当前请求的 trace_id**
2. 控制台彩色输出 + 文件按大小轮转
3. 提供结构化打点函数 `log_kv`

### 关键代码逐段拆解

#### ① ContextVar 而不是全局变量

```python
_trace_id_var: ContextVar[str] = ContextVar("trace_id", default="-")

def set_trace_id(trace_id: str | None = None) -> str:
    value = trace_id or new_trace_id()
    _trace_id_var.set(value)
    return value
```

**为什么不能用模块级全局变量 `current_trace_id = "..."`**：

asyncio 是**单线程并发**。请求 A 执行到一半 `await` 让出 CPU，
请求 B 开始执行并覆盖了全局变量，等 A 恢复执行时，
它读到的 trace_id 已经是 B 的了 —— 日志全部串号。

`ContextVar` 是 Python 3.7+ 为 asyncio 设计的，**按协程上下文隔离**，
A 和 B 各读各的，互不干扰。

> **面试怎么讲**：
> "日志的 trace_id 我用 ContextVar 存的。用全局变量在 asyncio 下必然串号，
> 因为单线程内多个协程是交织执行的。ContextVar 是标准库为这个场景提供的，
> 它按协程上下文隔离，效果等价于其他语言里的 ThreadLocal，但在协程模型下工作。"

#### ② Filter 注入字段

```python
class TraceIdFilter(logging.Filter):
    def filter(self, record: logging.LogRecord) -> bool:
        record.trace_id = _trace_id_var.get()
        return True
```

日志格式串里的 `%(trace_id)s` 需要 `record` 上有 `trace_id` 属性。
用 Filter 的好处是：**业务代码完全不用关心 trace_id**，
`logger.info("xxx")` 写在任何地方都会自动带上。

#### ③ 一个容易忽略的细节：恢复 levelname

```python
def format(self, record: logging.LogRecord) -> str:
    color = _COLORS.get(record.levelname, "")
    original = record.levelname
    record.levelname = f"{color}{original}{_RESET}"
    try:
        return super().format(record)
    finally:
        record.levelname = original   # ← 必须恢复
```

**为什么必须恢复**：同一个 `LogRecord` 对象会被**所有 handler 依次处理**。
控制台 handler 加完颜色后，如果不还原，文件 handler 拿到的 levelname
就是带 ANSI 转义码的字符串 —— 日志文件里会出现 `^[[32mINFO^[[0m` 这种乱码。

> 这是"彩色日志"实现里最常见的 bug。用 `try/finally` 保证即使格式化抛异常也能还原。

#### ④ 降噪

```python
for noisy in ("httpx", "httpcore", "urllib3", "chromadb", "sentence_transformers"):
    logging.getLogger(noisy).setLevel(logging.WARNING)
```

这些库在 INFO 级别输出极其啰嗦（httpx 会把每个 HTTP 请求的 header 都打出来）。
不降噪的话，你自己的业务日志会被淹没。

#### ⑤ 结构化打点

```python
def log_kv(logger, event: str, **kwargs) -> None:
    pairs = " ".join(f"{key}={value}" for key, value in kwargs.items())
    logger.info("%s | %s", event, pairs)
```

用法：`log_kv(logger, "retrieval.done", stage="vector", top_k=20, cost_ms=31.2)`

输出：`retrieval.done | stage=vector top_k=20 cost_ms=31.2`

**为什么不用 f-string 拼日志**：`logger.info("%s | %s", event, pairs)` 这种
**惰性格式化**只在日志真的要输出时才拼字符串。如果日志级别被过滤掉，
拼接操作就不会执行。在 DEBUG 级别日志很多时，这个优化有实际意义。

## 四、core/exceptions.py —— 异常体系

### 核心设计：把"业务错误"和"HTTP 状态码"解耦

```python
class AppException(Exception):
    code: ErrorCode = ErrorCode.INTERNAL_ERROR
    http_status: int = 500
    message: str = "服务内部错误"

    def __init__(self, message=None, *, code=None, http_status=None, detail=None):
        self.message = message or self.message
        ...
```

子类只需要声明三个类属性：

```python
class DocumentNotReadyError(AppException):
    code = ErrorCode.DOC_NOT_READY
    http_status = 409
    message = "文档尚未完成向量化, 暂时无法问答"
```

业务代码里就变成一行：

```python
raise DocumentNotReadyError(f"文档 {doc_id} 正在解析中")
```

**对比"到处 raise HTTPException"的写法**：

| | `raise HTTPException(status_code=409, detail="...")` | 本项目的 `AppException` |
|---|---|---|
| 业务层依赖 | 强依赖 FastAPI，无法在 Worker 里复用 | 纯 Python，任何地方都能用 |
| 错误码 | 只有 HTTP 状态码，前端无法区分细分类别 | 机器可读的 `code`，前端可差异化处理 |
| 文案 | 散落各处，难以统一改 | 集中在异常子类里 |
| 测试 | 要断言 HTTP 细节 | 直接 `pytest.raises(DocumentNotReadyError)` |

**关键点：Worker 里没有 HTTP 概念**。文档解析是在后台任务里跑的，
如果解析层抛的是 `HTTPException`，就说明业务逻辑被 Web 框架污染了。
本项目 `services/` 层不依赖 FastAPI，所以同一个异常在 HTTP 接口和后台任务里都能用。

### ErrorCode 为什么用 StrEnum

```python
class ErrorCode(StrEnum):   # 而不是 class ErrorCode(str, Enum)
    OK = "OK"
```

Python 3.11+ 引入的标准写法。区别：

```python
# class ErrorCode(str, Enum)
str(ErrorCode.OK)        # 'ErrorCode.OK'   ← 日志里很难看
f"{ErrorCode.OK}"        # 'ErrorCode.OK'

# class ErrorCode(StrEnum)
str(ErrorCode.OK)        # 'OK'             ← 干净
f"{ErrorCode.OK}"        # 'OK'
```

因为它本身继承 `str`，所以 `ErrorCode.OK == "OK"` 为 True，
可以直接做 JSON 序列化，也可以直接和字符串比较。

## 五、core/response.py —— 统一响应

### 约定

```json
{"code": "OK", "message": "success", "data": {...}, "trace_id": "a1b2c3d4e5f6"}
```

**为什么必须有 `trace_id`**：用户报障时只会说"我点了一下就报错了"。
如果响应里带 trace_id，用户截个图，你就能直接 `grep a1b2c3d4e5f6 logs/docmind.log`
把这次请求的完整日志捞出来。没有它，你只能靠时间戳猜。

**为什么 `ok()` / `fail()` 返回 `dict` 而不是 `ApiResponse` 实例**：
直接返回 dict 时 FastAPI 会做一遍 Pydantic 校验，有性能开销。
而这两个函数的输出结构是固定的、内部可信的，不需要再校验一遍。
`ApiResponse` 模型保留下来是**给 OpenAPI 文档用的**（描述响应结构），
运行时走轻量路径。

> **面试怎么讲**：
> "统一响应外壳的价值有两个：前端可以写一套拦截器处理所有错误；
> 以及响应里带 trace_id，用户报障时能直接定位到日志。
> 我把 ok/fail 写成返回 dict 而不是 Pydantic 模型，是为了省掉一次运行时校验 ——
> 内部构造的数据不需要再校验。"

### PageData

预留的分页结构，P1 的文档列表接口会用到。

## 六、core/middleware.py —— 中间件

### 两个能力合并成一个中间件

```python
class TraceIdMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        trace_id = set_trace_id(request.headers.get(TRACE_HEADER))
        request.state.trace_id = trace_id

        started = time.perf_counter()      # ← 用 perf_counter 而不是 time.time
        status_code = 500                   # ← 默认值 500
        try:
            response = await call_next(request)
            status_code = response.status_code
            response.headers[TRACE_HEADER] = trace_id
            return response
        finally:
            elapsed_ms = (time.perf_counter() - started) * 1000
            ...
```

**三个细节值得讲**：

**① 用 `time.perf_counter()` 而不是 `time.time()`**
`time.time()` 是墙钟时间，会被 NTP 校时、系统休眠影响，可能算出负数耗时。
`perf_counter()` 是单调递增的高精度计数器，专门用于测量时间间隔。

**② `status_code = 500` 作为默认值**
如果 `call_next` 抛异常（被异常处理器转成 500 响应前），
我们也要能记录到一个合理的状态码。这样访问日志里不会出现 `status=None`。

**③ 复用上游 trace_id**
```python
trace_id = set_trace_id(request.headers.get(TRACE_HEADER))
```
如果请求头里带了 `X-Trace-Id`（比如来自网关或前端），就复用它。
这样**跨服务的链路能串成一个 id**。取不到才新生成。

### 慢请求告警

```python
SLOW_REQUEST_MS = 3000.0
record = logger.warning if elapsed_ms >= SLOW_REQUEST_MS else logger.info
```

超过 3 秒的请求降级成 WARNING，这样 `grep WARNING` 就能快速找到性能劣化的接口。

### BaseHTTPMiddleware 的性能代价（进阶考点）

`BaseHTTPMiddleware` 使用起来最方便，但它**不是纯 ASGI 中间件**。
它的实现方式是在应用外面套一层 anyio task group，
每个请求都会额外创建一个 task —— 在高并发下有可测量的开销。

纯 ASGI 中间件的写法是直接实现 `__call__(self, scope, receive, send)`，
没有额外 task 开销，但代码复杂得多（要自己处理 `http` / `websocket` / `lifespan` 三种 scope）。

**本项目的取舍**：这是一个内部工具，QPS 不会高到需要抠这点开销，所以选可读性。
如果要做高并发网关，会改成纯 ASGI 实现。

> **面试怎么讲**：
> "我知道 BaseHTTPMiddleware 有额外 task 开销，纯 ASGI 中间件性能更好。
> 但这里的取舍是可读性优先 —— 这个系统的瓶颈在 LLM 调用（秒级），
> 不在中间件的几十微秒。如果换成高并发场景我会改写成纯 ASGI 实现。"

### 为什么静默部分路径

```python
_SILENT_PATHS = ("/docs", "/redoc", "/openapi.json", "/favicon.ico")
```

Swagger UI 加载时会请求一堆静态资源，全记日志会把有用的信息淹掉。

## 七、main.py —— 应用工厂与全局异常处理

### ① 应用工厂模式

```python
def create_app() -> FastAPI:
    app = FastAPI(...)
    ...
    return app

app = create_app()
```

**为什么用工厂函数而不是直接在模块顶层创建**：
测试里可以调用 `create_app()` 创建**多个隔离的实例**，
配合不同的环境变量跑不同的配置，互不干扰。
如果只有一个模块级 `app`，测试之间会共享状态。

### ② lifespan 生命周期

```python
@asynccontextmanager
async def lifespan(_app: FastAPI) -> AsyncGenerator[None, None]:
    setup_logging()
    settings.ensure_dirs()
    logger.info("DocMind 启动中 ...")
    ...
    yield          # ← 应用在这期间运行
    logger.info("DocMind 正在关闭 ...")
    _shutdown_embedding()
```

`yield` 之前是启动逻辑，之后是关闭逻辑。

**为什么不用 `@app.on_event("startup")`**：那个 API 已被 FastAPI 标记为 deprecated，
官方推荐用 lifespan（因为 `on_event` 无法保证启动/关闭逻辑成对出现）。

**启动时做的事**：
- `setup_logging()` —— 必须最先，否则后面的日志没有格式
- `settings.ensure_dirs()` —— 目录不存在时后面写文件会失败，要提前建
- 打印关键配置 —— 排查问题时第一眼就能确认"服务用的是哪个模型、哪个环境"
- 检查 API Key 并告警 —— **启动时就告诉用户少配了什么**，而不是等他调用问答接口才报错

**关闭时做的事**：释放本地模型占用的显存。这里是防御式写法：

```python
try:
    from app.services.embedding import release_models
    release_models()
except ImportError:
    pass   # P1 之前该模块还不存在, 属于预期情况
```

**为什么捕获 ImportError**：P0 阶段 `app.services.embedding` 还没写。
如果不捕获，P0 阶段每次关闭服务都会报错。这是一种**渐进式开发**的处理方式 ——
先埋好钩子，等模块实现了自动生效。

> **面试怎么讲**：
> "我把模型释放放在 lifespan 的关闭阶段，并且用 ImportError 兜底。
> 这样分阶段开发时，钩子可以先埋好，不用等到模块写完才能跑。"

### ③ 四个异常处理器（按优先级从具体到宽泛）

FastAPI/Starlette 的异常处理是**从最具体的类型开始匹配**的。

```python
@app.exception_handler(AppException)              # 自己的业务异常 → 用异常自带的 http_status
@app.exception_handler(RequestValidationError)    # 参数校验失败   → 400 + 字段级错误
@app.exception_handler(StarletteHTTPException)    # 404/401 等    → 映射到对应的 ErrorCode
@app.exception_handler(Exception)                 # 兜底           → 500，绝不泄露堆栈
```

**`RequestValidationError` 的处理值得讲**：

```python
details = [
    {"field": ".".join(str(x) for x in err.get("loc", ())), "reason": err.get("msg", "")}
    for err in exc.errors()
]
```

Pydantic 原始的错误结构嵌套很深（`loc` 是个 tuple，形如 `("body", "question", 0)`）。
这里把它压平成 `{"field": "body.question.0", "reason": "..."}`，
前端可以直接把 `field` 映射到表单字段上做高亮提示。

**兜底处理器的安全考虑**：

```python
logger.exception("未捕获异常 | path=%s", request.url.path)   # 完整堆栈进日志
return JSONResponse(status_code=500, content=fail(
    ErrorCode.INTERNAL_ERROR, "服务内部错误, 请稍后重试",
    {"trace_id": trace_id} if settings.debug else None,      # 只在 debug 下透出
))
```

**堆栈信息绝不能返回给前端** —— 会泄露文件路径、依赖版本、数据库结构。
但必须**完整打进日志**，否则线上问题无法排查。
debug 模式下才额外返回 trace_id 方便调试，生产环境连这个都不给。

> **面试怎么讲**：
> "未捕获异常我做了两件事：完整堆栈进日志保证可排查，但返回给前端的只有一句通用提示
> 和一个 trace_id。因为堆栈会暴露文件路径和依赖版本，是典型的信息泄露。
> 用户拿 trace_id 来报障，我从日志里定位 —— 这样既不泄露信息又不影响排障。"

### ④ CORS

```python
app.add_middleware(CORSMiddleware,
    allow_origins=settings.cors_origins,
    allow_credentials=True,
    expose_headers=["X-Trace-Id"],   # ← 这个必须显式声明
)
```

**`expose_headers` 的必要性**：浏览器出于安全考虑，默认**不允许 JS 读取跨域响应的自定义头**。
不声明 `expose_headers`，前端 `response.headers.get("X-Trace-Id")` 会拿到 `null`，
trace_id 机制在前端就断了。

**`allow_credentials=True` 与 `allow_origins=["*"]` 不能共存** ——
这是 CORS 规范的限制（凭据请求必须有明确的 origin）。所以本项目用的是显式列表。

### ⑤ 中间件注册顺序

```python
app.add_middleware(TraceIdMiddleware)
app.add_middleware(CORSMiddleware, ...)
```

Starlette 的中间件是**后注册的在外层**。所以实际执行顺序是：

```
请求 → CORSMiddleware → TraceIdMiddleware → 路由
```

**为什么 CORS 要在外层**：预检请求（OPTIONS）需要在进入业务逻辑之前就被 CORS 中间件短路处理掉。
如果 TraceId 在外层，预检请求也会被记录日志，产生噪音。

## 八、api/ —— 接口层

### router.py：路由聚合

```python
api_router = APIRouter()
api_router.include_router(health.router, prefix="/health", tags=["健康检查"])
# P1: api_router.include_router(documents.router, prefix="/documents", ...)
```

在 `main.py` 里统一挂载前缀：

```python
app.include_router(api_router, prefix=settings.api_prefix)   # /api/v1
```

**为什么要做 `/api/v1` 版本前缀**：接口一旦对外就不能随便改结构。
有版本号意味着可以同时提供 `/api/v1` 和 `/api/v2`，让调用方平滑迁移。

**为什么把 prefix 放在 include 而不是装饰器上**：前缀集中在一处，
`settings.api_prefix` 可以整体切换（比如灰度时挂到 `/api/v2beta`）。

### health.py：存活探针 vs 就绪探针

**这是 K8s 部署的标准概念，面试常问**：

| | 存活探针 `/health` | 就绪探针 `/health/ready` |
|---|---|---|
| 检查什么 | 进程还在不在 | 关键依赖能不能用 |
| 失败后果 | **重启容器** | **摘除流量，不重启** |
| 开销 | 必须极低 | 可以稍高（探测依赖） |
| 本项目实现 | 只返回内存里的元信息 | 真实探测 6 项依赖 |

**如果搞混会怎样**：把依赖检查放进存活探针，
数据库一抖动，K8s 会把所有容器全部重启 —— 本来只是暂时连不上，
结果引发了更大范围的雪崩。这是很经典的生产事故。

**就绪探针为什么不直接 import 而是用 `find_spec`**：

```python
def _check_package(module_name: str) -> tuple[bool, str]:
    found = importlib.util.find_spec(module_name) is not None
    return found, "已安装" if found else f"未安装 ({module_name})"
```

`find_spec` 只查模块是否存在，**不执行导入**。
如果直接 `import sentence_transformers`，会真的把模型加载进内存 ——
一个健康检查要跑几十秒、吃几个 GB 内存，显然不可接受。

**阻塞项与非阻塞项的区分**：

```python
blocking = ("workspace", "embedding", "vector_store")
ready = all(details[name]["ready"] for name in blocking)
```

`llm` 未配置**不算未就绪**。因为文档上传/入库链路依然完全可用，
只有问答不可用。如果把它算作阻塞项，探针会把这个实例从负载均衡里摘掉，
白白损失了 50% 的功能。

> **面试怎么讲**：
> "就绪探针我区分了阻塞项和非阻塞项。LLM 没配 Key 不影响文档解析入库，
> 如果算成未就绪，K8s 会把实例摘掉，等于把能用的功能也一起停了。
> 但问题依然要能被看见 —— 所以明细里会显示 `llm: ready=false`。"

## 九、tests/ —— 测试为什么这么写

### conftest.py 最关键的一点：环境变量必须在 import 之前设置

```python
os.environ.setdefault("DOCMIND_DATA_DIR", str(_TMP_ROOT / "data"))
os.environ.setdefault("DOCMIND_APP_ENV", "test")
...
# ↓ 必须在这之后才能 import
from app.main import create_app  # noqa: E402
```

**为什么**：`config.py` 的最后一行是 `settings: Settings = get_settings()` ——
**模块被导入的瞬间配置就已经实例化了**。如果先 import 再改环境变量，
配置早就定格了，改环境变量没有任何作用。

所以 `# noqa: E402`（禁止非顶部导入）在这里是**必须的**，不是偷懒。

**每个测试跑在独立的临时目录**：`tempfile.mkdtemp()` 建临时根目录，
所有落盘路径都指向它。这样跑测试不会污染开发环境的 `data/` 和 Chroma 库。

**为什么用 `setdefault` 而不是直接赋值**：允许外部通过环境变量覆盖
（比如 CI 里指定一个特定目录），同时保证没有外部设置时有合理默认值。

### client fixture 是 session 级的

```python
@pytest.fixture(scope="session")
def client() -> Iterator[TestClient]:
    with TestClient(create_app()) as test_client:
        yield test_client
```

**为什么是 session 而不是 function 级**：P1 之后应用启动会加载本地模型（几秒到几十秒）。
如果每个测试函数都重建应用，测试套件会慢到没人愿意跑。
用 session 级只建一次。

**`with TestClient(...)` 的 with 语句是必须的**：它会触发 lifespan 的启动/关闭钩子。
不写 `with` 的话，`setup_logging()` 和 `ensure_dirs()` 都不会执行。

### 测试覆盖了什么

```python
test_root_returns_service_meta           服务元信息
test_liveness_ok                          存活探针
test_readiness_reports_each_dependency    就绪探针返回逐项明细（而不是笼统 ok）
test_trace_id_header_is_echoed            链路 id 回传
test_trace_id_generated_when_absent       无链路 id 时自动生成
test_response_envelope_is_uniform         所有接口共用同一响应外壳
test_404_uses_unified_error_body          404 也走统一错误体
```

`test_config.py` 里则专门保护踩过坑的地方：

```python
test_comma_separated_extensions_are_parsed   # ← 就是那个 NoDecode 的坑
test_relative_paths_are_resolved_to_absolute
test_default_retrieval_params_are_sane       # 参数之间的自洽性
```

`test_default_retrieval_params_are_sane` 值得一说：

```python
assert 0 < cfg.final_top_k <= max(cfg.vector_top_k, cfg.bm25_top_k)
assert cfg.child_chunk_size < cfg.parent_chunk_size
```

这类**跨字段的约束校验**能防止"改了一个参数忘了改另一个"导致的隐性 bug。

## 十、scripts/check_env.py —— 环境自检

### 为什么值得单独写一个脚本

RAG 项目的失败原因 **80% 不在代码，而在环境**：缺依赖、模型没下载、
Key 没配、镜像没设、目录不可写。

与其让用户跑到某一步才报错，不如启动前花两秒全量体检。

### 设计要点

**① 分级：FAIL vs WARN**

```python
REQUIRED = {"fastapi": "...", "fitz": "...", ...}    # 缺了 → FAIL
OPTIONAL = {"sentence_transformers": "...", ...}     # 缺了 → WARN
```

区分"缺了就跑不起来"和"缺了只是某个功能不可用"。
全是 FAIL 的报告会让人麻木，全是 WARN 又会被忽略。

**② 延迟导入**

```python
try:
    import torch
    ...
except ImportError:
    record(WARN, "PyTorch", "未安装")
```

在 `try` 里 import，才能优雅处理"包不存在"的情况。

**③ 退出码**

```python
return 1 if fails else 0
```

有 FAIL 就返回非 0 退出码，这样可以串进 CI：
`check_env.py && pytest && uvicorn ...`

**④ Windows 编码处理**

```python
if sys.platform == "win32":
    for _stream in (sys.stdout, sys.stderr):
        with suppress(Exception):
            _stream.reconfigure(encoding="utf-8")
```

Windows 控制台默认 GBK(cp936)，打印中文会乱码，
极端情况下直接抛 `UnicodeEncodeError` 把脚本打断。

**⑤ 真实探测网络端口**

```python
sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
sock.settimeout(0.5)
reachable = sock.connect_ex((host, port)) == 0
```

`connect_ex` 返回错误码而不是抛异常，配合 0.5 秒超时，
能在不阻塞的前提下判断服务是否在监听。

## 十一、工程化文件

### Dockerfile

**① 多阶段构建**

```dockerfile
FROM python:3.11-slim AS builder    # 装依赖（需要 build-essential 编译工具）
...
FROM python:3.11-slim AS runtime    # 只拷贝装好的包
COPY --from=builder /install /usr/local
```

构建阶段需要编译器，运行阶段不需要。
多阶段构建让最终镜像里**不含编译工具链**（体积小、攻击面小）。

**② 依赖层单独缓存**

```dockerfile
COPY requirements.txt .          # ← 只复制依赖清单
RUN pip install -r requirements.txt
COPY . /app                      # ← 业务代码在后面复制
```

Docker 的层缓存是**从上到下逐层匹配**的。
把 `COPY . /app` 放在依赖安装之后，意味着**改业务代码不会触发重新装依赖**。
如果顺序反了，每次改一行 Python 代码都要重装几分钟的依赖。

**③ CPU 版 torch（最大的体积优化）**

```dockerfile
RUN pip install --prefix=/install \
    --extra-index-url https://download.pytorch.org/whl/cpu torch
```

默认的 `pip install torch` 会拉 CUDA 运行时，**约 2.5GB**。
容器里通常没有 GPU，装 CUDA 版纯属浪费。
换成 CPU 版后镜像从 ~5GB 降到 ~1.2GB。

> **面试怎么讲**：
> "镜像优化的最大收益来自把 torch 换成 CPU 版 —— 默认版会拉 2.5GB 的 CUDA 运行时，
> 而容器里根本没有 GPU。这一项就把镜像从 5GB 压到 1.2GB。
> 其次是多阶段构建和依赖分层缓存，前者去掉编译工具链，后者让改代码不触发重装依赖。"

**④ 非 root 用户运行**

```dockerfile
RUN useradd --create-home --shell /bin/bash docmind
USER docmind
```

容器逃逸时的最小权限原则。这是**安全基线**要求，很多扫描工具会直接告警。

**⑤ HEALTHCHECK 复用业务语义**

```dockerfile
HEALTHCHECK CMD curl -fsS http://localhost:8000/api/v1/health || exit 1
```

而不是写个 `curl /` 返回 200 就算健康。

### docker-compose.yml

**为什么默认的 embedded 模式不需要 Docker**：
Chroma 的 embedded 模式内嵌在应用进程里，Redis 在 `inline` 模式下也不用。
所以 **`pip install` + 启动就能跑**，不需要任何中间件。

这对 GitHub 项目很重要：**别人 clone 下来能不能一次跑通，直接决定项目的可信度**。
Compose 是给"要水平扩展"的场景准备的。

**模型缓存卷**

```yaml
- model_cache:/app/models
```

api 和 worker 两个容器共享同一份下载好的模型，
避免每个容器都下载一遍 2GB 的权重。

### .gitattributes

```gitattributes
* text=auto eol=lf
*.cmd text eol=crlf
```

**为什么必须显式声明**：Windows 下 Git 默认把文本检出为 CRLF。
CRLF 会让**容器内的 shell 脚本执行失败** ——
shebang 行末尾多出一个 `\r`，Linux 会报 `no such file or directory`。

这个坑的恶劣之处在于：**本地开发完全正常**（Windows 上 `\r\n` 没问题），
一构建 Docker 镜像就炸，而且报错信息完全不指向真正的原因。

## 十二、面试追问预案

### Q：为什么用 FastAPI 不用 Django/Flask？

A：三个理由。一是原生 async —— RAG 问答要同时等待 LLM 流式响应和向量检索，
异步模型下可以并发而不是阻塞；二是 Pydantic 的类型校验和 OpenAPI 自动文档，
省掉大量样板代码；三是生态 —— 向量库、LLM SDK、评测框架几乎都优先支持 Python。
如果是团队 Java 栈，我会用 Spring Boot 做业务网关 + FastAPI 做 AI 能力层。

### Q：配置为什么不用 yaml/ini？

A：环境变量是**十二要素应用（12-Factor App）**的推荐方式，
容器化/云原生环境下天然支持（`docker run -e`、K8s ConfigMap/Secret）。
密钥类的配置绝对不能进代码仓库，环境变量是最自然的载体。
YAML 更适合复杂嵌套配置，但这里配置项是扁平的。

### Q：日志为什么要自己封装 Formatter？

A：为了统一格式 + 注入 trace_id + 控制台彩色。标准库的 `logging` 功能足够，
不需要引入 loguru 之类的第三方库 —— **少一个依赖就少一个维护负担和供应链风险**。
loguru 的好处是 API 更简洁，但对这种规模的项目不值得。

### Q：ContextVar 和 ThreadLocal 的区别？

A：概念上都是"每个执行上下文独占一份数据"。
区别在于 ThreadLocal 按线程隔离，ContextVar 按**协程上下文**隔离。
asyncio 是单线程内多协程并发，ThreadLocal 起不到隔离作用（所有协程共享同一个线程）。
ContextVar 是 Python 3.7 专门为此引入的。
另外 ContextVar 支持 `copy_context()` 传递，asyncio 的 `create_task` 会自动复制上下文。

### Q：异常处理器为什么不直接返回 `HTTPException`？

A：`HTTPException` 是"HTTP 层的错误"，而我们的业务错误（如"文档还没解析完"）
在后台任务里也会发生。业务层不应该依赖 Web 框架。
所以自定义 `AppException` 携带 `code` + `http_status`，
由全局处理器翻译成 HTTP 响应 —— 这是**依赖倒置**的应用。

### Q：健康检查为什么要两个端点？

A：（见第八节表格）核心是**失败后的动作不同**：
存活失败重启容器，就绪失败摘流量。搞混会导致依赖抖动引发全量重启雪崩。

### Q：lru_cache 做单例有什么问题？

A：三个问题。一是**测试时无法替换** —— 需要 `get_settings.cache_clear()`
或者在导入前设置好环境变量（本项目用的是后者）；二是**配置热更新做不到**，
改了 `.env` 必须重启进程；三是 `maxsize=1` 时如果带参数调用会互相驱逐，
但本函数无参数所以没问题。如果要做配置热更新，应该改用带过期时间的缓存
或者文件监听。

## 十三、自测题（能答上来说明真懂了）

1. 为什么 `config.py` 里既有 pydantic-settings 又有 `load_dotenv`？
2. `NoDecode` 解决的是什么问题？不加会发生什么？
