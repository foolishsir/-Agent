# 大文档处理方案

> 本文基于**实测数据**，而不是推测。先说结论：大文档的问题**不是"慢"**，
> 而是四个互相独立的工程问题，其中只有一个跟性能有关。

---

## 一、先测，再优化

### 实测数据（本机，RTX 4060）

| 文档 | 页数 | 字符 | 解析耗时 | ms/页 | 字体形态 |
|---|---|---|---|---|---|
| 合成文档（内置 CJK） | 200 | 278,000 | 1.03 s | **5 ms** | 单个嵌入子集 |
| 真实简历 | 2 | 2,864 | 1.36 s | **681 ms** | **Type3 逐字嵌入** |
| Docker 手册（扫描件） | 74 | 0 | 2.47 s | 33 ms | 无文本层（纯图片） |

**同一个 200 页文档，字体形态不同，解析耗时差 136 倍。**

| 环节 | 200 页耗时 | 占比 |
|---|---|---|
| 解析 | 1.03 s | 29% |
| 清洗 | 0.10 s | 3% |
| 分块 | 0.07 s | 2% |
| 向量化（1,068 子块） | 2.40 s | **67%** |
| **合计** | **3.60 s** | |

### 外推（合成文档，字体正常）

| 页数 | 预估总耗时 |
|---|---|
| 100 页 | 1.8 s |
| 500 页 | 9.0 s |
| 1000 页 | 18 s |

### 外推（Type3 字体，很多国产工具导出的 PDF 都是）

| 页数 | 解析耗时 | 说明 |
|---|---|---|
| 100 页 | 68 s | 已超过常见网关 60s 超时 |
| 500 页 | **5.7 分钟** | |
| 1000 页 | **11.3 分钟** | |

> **第一个反直觉的结论**：解析耗时与**页数**的相关性，远弱于它与**字体嵌入方式**的相关性。
> 同样是 200 页，5 ms/页 和 681 ms/页 是两回事。
> 所以"多少页算大文档"这个问题没有统一答案 —— **要看 PDF 是怎么生成的**。

## 二、四个独立问题

把"大文档处理"拆成四件事，它们的解法完全不同：

| # | 问题 | 性质 | 优先级 |
|---|---|---|---|
| 1 | **请求被阻塞** —— 10 分钟的活儿塞在一个 HTTP 请求里 | 架构 | **P0 必须做** |
| 2 | **进度不可见** —— 用户不知道在跑还是死了 | 体验 | **P0 必须做** |
| 3 | **失败要重来** —— 第 9 分钟挂了，前 8 分钟白费 | 可靠性 | P1 |
| 4 | **检索质量退化** —— 5000 个子块里，Top-20 可能全来自同一章 | 效果 | P1 |

**性能优化反而是 P2** —— 因为前三个问题不解决，跑得再快也没用：
网关 60 秒就把请求掐了，快慢都无所谓。

---

## 三、问题 1 & 2：异步任务 + 真实进度

### 现状

`DOCMIND_TASK_MODE=inline` 意味着整条流水线**在 HTTP 请求里同步执行**。
10 分钟的活儿一定会被网关（通常 60s）或浏览器掐断，而且用户看到的是一个
永远转圈、最后报错的页面。

### 方案

代码里其实**已经为这一步铺好了路**：

- `submit_ingest()` 已经有 inline / queue 两条分支
- 状态机 `PENDING → PARSING → EMBEDDING → READY/FAILED` 已经实现并落库
- `GET /documents/{id}/status` 接口已经有了
- 前端轮询逻辑已经写好了

要补的只有：**RQ + Redis 的 Worker 侧**。

```
POST /documents  →  落盘 + 建记录(PENDING) + 投递任务  →  立即返回 202
                                                          ↓
                        Worker 消费 → PARSING → EMBEDDING → READY
                                                          ↓
                        前端轮询 /documents/{id}/status  →  进度条
```

### 关键设计：进度不能是假的

现在的 `build_status_out()` 是按状态映射的**固定百分比**（PARSING=35%）。
对 10 分钟的任务，进度条会卡在 35% 九分钟 —— 用户会以为死了。

正确做法：**按实际处理单元上报进度**。

```python
# Worker 侧
job.meta["progress"] = 5 + int(90 * done_chunks / total_chunks)
job.meta["stage"] = "embedding"
job.save_meta()
```

进度单位应该是"**已处理的子块数 / 总子块数**"，而不是"页数" ——
因为向量化阶段 67% 的时间，按页数算进度会严重失真。

### 任务粒度：阶段拆分，不按页拆

| 粒度 | 优点 | 缺点 |
|---|---|---|
| 整份文档一个任务 | 实现最简单 | 失败全丢；进度粒度粗 |
| **按阶段拆分** | 可定位卡在哪一步；可只重跑失败阶段 | 需要编排 |
| 按页拆分 | 并行度高 | **解析必须整份做** —— 跨页页眉检测需要全文档统计 |

**推荐按阶段拆**：

```
Task 1  parse + clean + chunk  →  写 chunks 表(is_indexed=False)  →  PARSING
Task 2..N  embed 批次(每批 256 子块) → upsert + 逐批置 is_indexed=True  →  EMBEDDING
Task N+1  finalize  →  统计 + READY
```

## 四、问题 3：断点续传

### 现状

`run_ingest()` 是"要么全成，要么全不成"：分块结果在**最后一步**才写库。
10 分钟的任务在第 9 分钟失败 → 前面 9 分钟全部作废。

### 方案

**数据模型已经预留了字段**（当初就是为这个设计的）：

- `Chunk.is_indexed` —— 标记该分块是否已写入向量库
- `Document.chunks_indexed` —— 已索引数量

改成：**分块完成后立即落库**，然后逐批 embedding、逐批 upsert、
逐批把 `is_indexed` 置 True。重试时只补 `is_indexed=False` 的块。

```python
# 重试路径
pending = [c for c in chunks if not c.is_indexed]
if len(pending) < len(chunks):
    logger.info("断点续传: 跳过 %d 个已索引块", len(chunks) - len(pending))
```

配合**确定性 chunk id**（已实现），重跑是 upsert 覆盖而不是追加 ——
所以"重试"永远安全，不会产生重复数据。

## 五、问题 4：检索质量退化（**最容易被忽略**）

### 现象

500 页文档产生约 5,000 个子块。用户问一个具体问题，`Top-20` 可能**全来自同一章**，
上下文多样性归零。更糟的是父块去重后可能只剩 3~4 个父块，全是同一个小节的。

### 四个层次的解法

**① 元数据预过滤**（成本最低，收益最直接）

先缩小范围再检索，而不是在全库找。现在已支持 `doc_ids`，
可以扩展到**章节/页码范围**：

```python
where = {"doc_id": doc_id, "page_start": {"$gte": 30, "$lte": 60}}
```

用户如果知道答案在"第三章"，就直接过滤 —— 召回集从 5000 降到 200，
精度和速度同时提升。

**② MMR 多样性重排**（几行代码）

精排后做 Maximal Marginal Relevance：在"相关性"和"与已选结果的差异度"之间权衡，
避免 Top-5 全是同一段内容。

```python
# 简化版: 同一父块的子块最多选 N 个
```

**③ 分层索引**（效果最好，成本最高）

```
第一层: 章节摘要索引（每章一段话，约 50 条）
第二层: 章节内的细节块
```

检索时**先在摘要层定位章节，再在章节内检索细节**。
对"我该看哪一章"类的问题特别有效。

成本：多一次 embedding（摘要）+ 一次检索，但 500 页文档上精度提升明显。

**④ 目录页与低质量分块**

大文档的前几页常是封面、目录、版权页，会产生大量低质量分块
（"目录"、"第 1 章 …… 3"）。它们信息量极低却会参与检索。

方案：识别目录页特征（短行 + 大量省略号/数字），打上 `page_type=index` 标签，
检索时降权或过滤。

## 六、性能优化（P2，但值得做）

按**收益/成本**排序：

| 优化 | 预期收益 | 成本 | 备注 |
|---|---|---|---|
| **加大 embedding batch** | 可能 2~3× | 极低 | 现在 batch=32，4060 跑 512 维小模型可到 128+ |
| **解析并行化** | 2~4× | 中 | PyMuPDF 在 C 层释放 GIL，多线程可能有效，需实测 |
| **解析结果缓存** | 重复调参时 100% | 极低 | **已实现**（`chunk_preview.get_clean_document`） |
| **按页增量解析** | 仅增量场景 | 高 | 文档改一页只重解析一页 |
| **大文件分片上传** | 上传阶段 | 中 | 与处理无关，只解决传输 |

> **不要先做并行化**。实测下来 67% 的时间在向量化、29% 在解析，
> 而解析里 99% 的开销又集中在 Type3 字形解析上 ——
> **并行化能让这 29% 变快，但改变不了"11 分钟"这个量级**。
> 真正的解法是异步化（让用户不用等），而不是让它跑得更快。

## 七、实测中发现的一个真实风险：跨页去重可能误删内容

压测时发现：**200 页合成文档在清洗阶段从 2,800 个块掉到 505 个块，丢掉 82% 内容**。

原因是 `cleaner._dedupe_across_pages()`：任何 **≥40 字**的段落在**超过一页**上
出现，就被判定为模板噪音并删除（只保留第一次出现）。

去重逻辑本身是**对的** —— 它成功识别出了我的合成文档里每页重复的内容。
但它同时暴露了一个真实风险：

> **长文档里跨页重复的正常内容会被误删。**
>
> 例如一份 200 页的设备手册，每章开头都有一段同样的"安全须知" ——
> 它会被删到只剩第一章那一处。用户问第七章的安全要求时，
> 引用会指向第一章。

### 改进方向

| 方案 | 说明 |
|---|---|
| 收紧范围 | 只在**相邻页**去重（连续重复），而不是全文档范围 |
| 提高阈值 | ≥40 字太激进，模板噪音通常更长（整段），可提到 ≥150 字 |
| 保留位置信息 | 不删除，而是打 `is_repeated=True` 标签，检索时降权 |
| 加告警 | 当去重比例超过某个阈值（如 30%）时告警，提示可能误删 |

**推荐组合**：收紧到相邻页 + 超阈值告警。
因为"连续多页重复"几乎必然是页眉页脚或模板，
而"间隔很远的两页有相同段落"更可能是正常内容。

## 八、落地优先级

| 阶段 | 内容 | 工作量 | 价值 |
|---|---|---|---|
| **A** | RQ + Redis 异步化 + 真实进度上报 | 1~2 天 | **必须** —— 不解决则大文档完全不可用 |
| **B** | 分批 embedding + 逐批落库 + 断点续传 | 1 天 | 大文档失败不再全量重来 |
| **C** | 检索侧：元数据预过滤 + MMR 多样性 | 1 天 | 大文档的检索质量保障 |
| **D** | 跨页去重收紧 + 告警 | 0.5 天 | 修掉实测发现的误删风险 |
| **E** | embedding batch 调优 + 解析并行化 | 1~2 天 | 收益有限，最后做 |

**A + B 是必须做的**，C + D 是"大文档场景下才暴露"的优化，E 可选。

## 九、面试怎么讲

> "大文档处理我先做了实测，没有直接开始优化。结果发现三件事：
>
> **第一，解析耗时跟页数的关系远弱于跟字体嵌入方式的关系。**
> 同样 200 页，内置字体的 5 毫秒一页，Type3 逐字嵌入的 681 毫秒一页 ——
> 差 136 倍。所以'多少页算大'没有统一答案。
>
> **第二，瓶颈其实不在性能。** 实测 200 页需要 3.6 秒，其中 67% 在向量化。
> 但真正的问题是这个活儿在 HTTP 请求里同步跑 ——
> 换成 Type3 字体的 1000 页文档就是 11 分钟，网关 60 秒就掐断了。
> 所以优先级最高的是**异步化**，不是跑得更快。
>
> **第三，大文档的检索质量和处理速度是两回事。**
> 5000 个子块里 Top-20 可能全来自同一章，上下文多样性归零。
> 这个要在检索侧解决（元数据预过滤 + MMR 多样性重排），
> 而不是靠调大 Top-K。
>
> 另外压测时还意外发现一个真实风险：跨页重复内容去重会把长文档里
> 每章重复的正常内容误删 —— 200 页测试文档被删掉了 82%。
> 这说明**去重阈值必须结合文档规模重新校准**。"
