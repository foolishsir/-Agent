## 一、文档解析层

### 难点 1：PDF 是"排版格式"不是"语义格式" 🔴

**现象**：直接提取文本后，页眉页脚混进正文，双栏论文左右栏交错读串行，
跨页的句子被硬切断。

**根因**：PDF 只描述"某个字符画在哪个坐标"，不描述阅读顺序。
`page.get_text()` 按内部对象顺序输出，不保证是人类阅读顺序。

**方案**（分层处理）：

1. **用坐标而不是纯文本**：`page.get_text("dict")` 拿到每个文本块的 bbox 坐标。
2. **双栏检测**：统计所有文本块的 x 中心点分布。如果呈现明显的双峰（左栏/右栏），
   则按 x 坐标分左右两组，各组内按 y 排序后再拼接。
3. **页眉页脚自动识别**：不写死"去掉前 50 像素"。改为**跨页重复检测** ——
   把每一页的首/尾几行文本收集起来，若某行文本出现在超过 50% 的页面上，
   判定为页眉/页脚并剔除。这个方法对论文、手册、规范都通用，不需要针对每份文档调参。
4. **断行合并**：中文行尾没有连字符，若上一行末尾不是句末标点（。！？：；），
   且下一行开头不是标题序号，则合并。

**如何验证**：准备 3 份典型 PDF（单栏论文、双栏论文、带页眉页脚的手册），
解析后打印前 20 个 chunk，人工检查语义是否连续。

**面试怎么讲**：

> "PDF 解析的核心矛盾是它没有阅读顺序信息。我用 PyMuPDF 拿文本块的坐标，
> 通过 x 坐标聚类判断单双栏，通过跨页重复行检测自动识别页眉页脚。
> 用重复检测而不是固定位置，是因为不同文档的页眉高度不一样，
> 写死位置的话每换一份文档就要重新调参。"

---

### 难点 2：扫描件是纯图片 🟡

**现象**：解析后文本为空或只有零星几个字符，但文件明明有几十页。

**根因**：扫描件/图片型 PDF 里没有文本层。

**方案**：解析后统计每页有效字符数，低于 `OCR_FALLBACK_THRESHOLD`（默认 80）
判定为扫描页，走 OCR 降级链路（PaddleOCR / RapidOCR）。
**关键是要给出明确提示**，而不是静默返回空结果 —— 用户上传完看到"就绪"却问不出东西，体验最差。

**设计取舍**：OCR 是重量级依赖（PaddleOCR 会拉入好几个 GB 的模型）。
本项目把它做成**可选依赖**：默认不装，检测到扫描件时抛出 `DOC_OCR_REQUIRED`
并提示用户安装。这样保持了主链路轻量。

**面试怎么讲**：

> "我没有在项目里默认集成 OCR，因为它会给所有用户增加 2GB 依赖，
> 但 90% 的电子版 PDF 用不上。我做成按需降级 + 明确报错，
> 这是工程上对依赖膨胀的取舍。"

## 二、分块层

### 难点 3：切太碎丢语义，切太大检索不准 🔴

**现象**：固定 500 字切分后，检索命中的片段是"半句话"，LLM 回答不完整；
把块调大到 1500 字后，检索精度又明显下降。

**根因**：**检索粒度和生成粒度的最优解不同**。检索要小（语义聚焦、向量不被稀释），
生成要大（上下文完整）。单层分块无法同时满足。

**方案**：**父子块（Small-to-Big）双层索引**。

```
父块 1500 字（按章节标题切）
 └─ 子块 300 字 × N  ← 只有子块进向量库
```

- 检索命中子块 → 拿到 `parent_id` → 回查父块全文
- 多个子块命中同一父块 → **去重合并**，只送一份父块给 LLM

**额外收益**：因为父块去重，实际送进 Prompt 的 token 反而比"直接塞 20 个 300 字块"
少且完整。这是一个"精度和成本同时改善"的方案，比较少见。

**如何验证**：评测集上对比三种策略的 Recall@5（见 `docs/05-评测方案.md`）。

**面试怎么讲**：

> "分块的核心洞见是：检索和生成需要不同的粒度，所以不能只切一层。
> 我把子块用于建索引保检索精度，父块用于喂模型保上下文完整，
> 中间用 parent_id 关联。而且因为父块去重，token 反而更省了。"

---

### 难点 4：中文按字符数切分会在词语中间断开 🟡

**现象**：一句话被从"设备维护周" / "期是三个月"之间切断。

**方案**：切分时按优先级找分隔符 —— `\n\n`（段落）→ `\n`（行）→ `。！？；`（句）→ `，、`（读）→ 字符。
这是 LangChain `RecursiveCharacterTextSplitter` 的思路，但中文的分隔符集必须换掉
（英文的 `. ` 在中文里没有意义）。

**补充一个细节**：切分后要丢弃长度小于 `MIN_CHUNK_SIZE` 的碎片（如单独一个页码"12"），
否则这些碎片也会被向量化，污染检索结果。

## 三、检索层

### 难点 5：向量检索对型号、数字、专有名词不敏感 🔴

**现象**：问「1333 机种钢刀的更换周期」，召回的全是"设备维护""刀具管理"相关但机种不对的段落。

**根因**：Embedding 模型把文本压成语义向量时会**丢失精确的词面信息**。
`1333` 和 `1335` 在语义空间里几乎一样近，但对业务来说是天壤之别。

**方案**：**混合检索** —— 向量召回 Top-20 + BM25 关键词召回 Top-20，用 RRF 融合。

- 向量负责"意思对"
- BM25 负责"词对"（型号、编号、专有名词、数字）

BM25 中文需要分词，用 `jieba`；且必须把型号类 token 加入自定义词典，
否则 `1333` 可能被切碎。

**如何验证**：构造 10 条**包含精确型号/数字**的问题，对比纯向量 vs 混合检索的命中率。
这类问题的差距会非常明显，是最有说服力的实验数据。

**面试怎么讲**：

> "纯向量检索的失败模式很典型：语义相近但事实不同的内容分不开。
> 我加了 BM25 一路做混合检索。这里有个坑 —— RRF 融合只用排名不用分数，
> 否则向量的余弦相似度和 BM25 的分数根本不在一个量纲上，归一化方式又是个新的调参坑。"

---

### 难点 6：RRF 的 k 参数怎么选 🔴

**公式**：$\text{RRF}(d) = \sum_i \frac{1}{k + \text{rank}_i(d)}$

**k 的作用**：`k` 越小，排名靠前的文档权重差异越极端；`k` 越大，各排名权重越平均。

- `k=0`：第 1 名权重 1.0，第 2 名 0.5，第 3 名 0.33 —— 头部过于极端
- `k=60`：第 1 名 0.0164，第 2 名 0.0161 —— 更平滑，且**抗单路噪声**

**为什么默认 60**：这是原论文的经验值，且在大多数场景下表现稳定。
工程上不建议在这个参数上花太多时间，**先调 chunk 大小和 rerank 收益更大**。

---

### 难点 7：召回率和延迟的权衡 🟡

**现象**：把 `TOP_K` 从 20 调到 100，召回率涨了，但响应时间从 2s 涨到 8s。

**根因**：Rerank 是 O(n) 次前向计算。召回 100 条就要跑 100 次交叉编码器。

**方案**：分层控制。

| 阶段 | 数量 | 手段 |
|---|---|---|
| 全量 → 候选 | 20 + 20 | 向量 + BM25，毫秒级 |
| 候选 → 精排 | 20（去重后） | RRF 融合，零成本 |
| 精排 → 入 Prompt | 5 | Cross-Encoder，300ms 级 |

**面试怎么讲**：

> "召回和精排是一对取舍：召回要快要宽，精排要准要窄。
> 我的配置是 20+20 召回、融合后精排、取 Top-5 进 Prompt。
> 如果要再提召回率，我会优先改 chunk 策略和 embedding 模型，
> 而不是无脑加大 Top-K —— 后者边际收益递减，延迟是线性增长的。"

## 四、生成层

### 难点 8：LLM 幻觉 —— 文档里没有的也能编 🔴

**现象**：问文档里没写的内容，模型依然给出一个看起来很专业的答案。

**根因**：LLM 的训练目标是"生成通顺的回答"，不是"承认不知道"。
单纯在 Prompt 里写"不知道就说不知道"只能缓解，不能根治。

**方案**：**四道防线**，层层收紧。

| 防线 | 手段 | 可靠性 |
|---|---|---|
| 1. 检索侧 | 精排最高分 < 阈值 → 直接拒答，**根本不调用 LLM** | 高 |
| 2. Prompt 侧 | 明确约束"仅依据片段回答" + 少量示例 | 中 |
| 3. 结构侧 | 要求逐句标注 `[编号]`，编号对应上下文 | 中 |
| 4. **服务端校验** | 解析答案里的引用编号，**校验编号是否真实存在于上下文**，不存在的引用剥离或整段拒答 | 高 |

**关键认识**：防线 1 和 4 是**代码层面的硬约束**，不依赖模型"听话"。
面试时这一点很重要 —— 说"我靠 Prompt 防幻觉"是初级答案，
说"我知道 Prompt 不可靠，所以在代码层做了校验"才是工程答案。

**如何验证**：评测集里放 10 条**文档中不存在答案**的问题，统计拒答率。
理想情况下拒答率应接近 100%，误答率接近 0。

---

### 难点 9：Token 爆炸与 Lost in the Middle 🟡

**现象**：塞 20 个块进 Prompt，token 上万，又贵又慢；而且模型对**中间位置的上下文**
注意力明显下降，容易忽略关键信息。

**根因**：两个独立问题叠加 —— 上下文长度成本是线性的，但模型对长上下文的利用是非均匀的。

**方案**：

1. **父子块去重** —— 20 个子块可能只对应 4 个父块，token 直接降一个数量级
2. **精排截断** —— 只取 Top-5
3. **顺序编排** —— 把精排分数最高的放在**最前和最后**，次高的放中间（对抗 Lost-in-the-Middle）
4. **上下文压缩**（可选）—— 超长时先用小模型对每个片段做摘要再拼

**面试怎么讲**：

> "很多人只盯着'怎么塞更多上下文'，但长上下文有边际递减甚至负收益 ——
> 这就是 Lost in the Middle。我的做法是先把上下文量降下来（父子块去重 + 精排截断），
> 再考虑顺序编排，把最相关的放头尾。"

## 五、并发与工程化

### 难点 10：大文件解析阻塞请求 🟡

**现象**：上传 50MB 扫描版 PDF，接口转圈 2 分钟，被网关 504 掐断。

**方案**：异步任务流水线。

- 上传接口只做**校验 + 落盘 + 投递队列**，立即返回 `202 + task_id`
- 前端轮询 `GET /documents/{id}` 拿状态
- 任务表用**状态机**：`PENDING → PARSING → EMBEDDING → READY / FAILED`

**为什么不用 `ready` 布尔值**：长事务中间失败时，布尔值无法告诉你失败在哪一步，
重试就只能整份重跑。状态机让重试可以精确到阶段。

**面试怎么讲**：

> "这里其实和我之前做数据同步遇到的问题同构 —— 长链路任务必须有状态机，
> 否则失败重试的粒度太粗。我把解析拆成解析/清洗/分块/向量化四个可观测阶段，
> 每步都落库，失败能定位到具体阶段。"

---

### 难点 11：重复上传产生重复向量 🟡

**现象**：用户网络卡了点了两次上传，向量库里同一份文档存了两遍，检索结果里出现重复引用。

**方案**：**内容 MD5 作为幂等键**。

- 上传时先算文件 MD5，查库
- 已存在且 `READY` → 直接返回已有 `doc_id`（秒传）
- 已存在但处理中 → 返回已有任务状态，不重复投递
- 已存在但 `FAILED` → 复用原记录并重试

**注意**：文件级 MD5 不够 —— **用户改了文件名重新上传，MD5 不变，应该判定为同一份**；
反之，同一份文件改了内容，MD5 变了，应该判定为新文档。用内容 hash 而不是文件名，正是这个原因。

---

### 难点 12：删除文档后检索到"幽灵数据" 🟡

**现象**：删除了文档，向量库里的 chunk 还在，检索时还能召回出来。

**根因**：向量库和关系库是两个独立的存储，没有跨库事务。

**方案**：**三段式删除**。

```
① 关系库标记 status=DELETED（立即对用户不可见，秒级生效）
② 异步清理向量库中该 doc_id 的所有 chunk
③ 可选：清理原文件 + 硬删记录
```

**兜底**：检索时**强制过滤 `doc_id in (有效文档列表)`**。
即使清理任务失败了，也不会检索到已删内容 —— 用查询过滤做最终一致性保护。

**面试怎么讲**：

> "跨存储的删除没有事务可用，所以我用了'先软删再异步清理'，
> 并且在检索侧加了兜底过滤。宁可短暂不可见，也不能检索到已删内容 ——
> 这是业务上唯一可接受的方向。"

---

### 难点 13：多用户数据隔离 🟡

**现象**：A 用户提问，检索到了 B 用户的文档片段。

**方案**：`user_id` 写进**向量库的元数据**，检索时**带上 where 过滤条件**。

```python
collection.query(
    query_embeddings=[vec],
    where={"user_id": {"$eq": user_id}},   # ← 必须下沉到向量库
    n_results=20,
)
```

**为什么不能在应用层过滤**：向量库先召回 Top-20，应用层再过滤掉别人的，
如果你的文档占了绝大多数，Top-20 可能被过滤到只剩 1 条 —— 召回质量崩塌。
**过滤条件下沉到向量库，是在候选生成阶段就排除，而不是事后筛。**

这是一个很容易被忽略、但面试官很爱问的点。

---

### 难点 14：Embedding 重复计算浪费成本 🟡

**现象**：同一份文档被重复处理、或多用户上传相同模板文档，每次都重新算一遍 embedding。

**方案**：**内容 hash 缓存**。

- `chunk.content` 的 SHA256 作为 key，查 Redis / 本地缓存拿向量
- 命中则直接复用，未命中才调用模型

**收益**：文档更新场景下（改了一页重新上传），只有变化的 chunk 需要重算。
100 页文档改 1 页，embedding 计算量从 100% 降到 ~1%。

---

### 难点 15：本地模型的冷启动开销 🟡

**现象**：服务启动后第一个问答请求要等 30 秒。

**根因**：`SentenceTransformer` 首次加载要从磁盘读模型权重并初始化计算图。

**方案**：

1. 在 FastAPI 的 `lifespan` 启动钩子里**预热**（加载模型 + 跑一次 dummy 推理）
2. 模型对象做**进程级单例**（用 `lru_cache` 装饰工厂函数）
3. 推理加 `torch.inference_mode()` 关闭梯度计算，省显存和时间
4. 容器部署时**模型目录挂载成 volume**，避免每次重建镜像重新下载 2GB

**面试怎么讲**：

> "本地模型是进程级单例 + 启动预热。如果不预热，第一个用户会等 30 秒，
> 这在生产上是不可接受的。另外容器里我把模型缓存目录挂成了 volume，
> 多个副本共享同一份权重。"

---

## 六、效果度量

### 难点 16：改完不知道有没有变好 🔴（方案已定，数据待产出）

**现象**：调完 Prompt "感觉好像好一点"，但说不出具体提升。面试被问"你怎么衡量效果"直接卡住。

**根因**：RAG 是**多阶段链路**，最终答案的好坏无法定位到具体环节。

**方案**：**分层评测 + Golden Set**。

先建 40 条评测样本，每条包含：`问题` + `标准答案` + `应命中的 chunk id`。

| 层级 | 指标 | 衡量什么 |
|---|---|---|
| 检索层 | Recall@K | 该召回的 chunk 有没有进候选集 |
| 检索层 | MRR | 正确的 chunk 排得够不够前 |
| 生成层 | Faithfulness（忠实度） | 答案是否完全由上下文支撑，有无编造 |
| 生成层 | Answer Relevancy | 答案是否切题 |
| 生成层 | Context Precision | 送进 Prompt 的上下文里有多少是真有用的 |
| 工程层 | 首 token 延迟 P95 / 总耗时 | 用户体验 |
| 工程层 | 单次问答 token 成本 | 钱 |

**关键认识**：**检索指标必须单独测**。因为答案不好时，你无法区分是"没检索到"
还是"检索到了但 LLM 没用对"。分层评测就是为了把问题定位到环节。

**面试怎么讲**（这是拉开差距的地方）：

> "大部分 RAG demo 的问题是没有评测。我建了一套 40 条 Golden Set，
> 把指标拆成检索层和生成层。因为我发现只看最终答案准确率没法定位问题 ——
> 答案错可能是召回没召到，也可能是召回了 LLM 没用对，
> 这两种情况的优化方向完全相反。"

---

### 难点 17：评测集从哪来 ⚪

**方案**（三条路径，按成本排序）：

1. **从真实使用中沉淀**：问答接口加点踩反馈，点踩的问题人工标注后进评测集。
   这是最真实的来源，但需要时间积累。
2. **LLM 辅助生成**：把文档分块喂给 LLM，让它生成"这个块能回答的问题"。
   生成快，质量需要人工复核。**注意要包含一部分"文档中无答案"的问题**，用来测拒答能力。
3. **人工构造**：针对关键业务场景手写 10~20 条。量少但质量最高。

**当前项目采用**：2 + 3 结合，生成后用人工筛选。评测集放在 `eval/golden_set.jsonl`。

## 七、已知边界（面试主动说明）

这些问题**当前版本没有解决**，主动说明能体现技术判断力：

| 边界 | 影响 | 如果要解决 |
|---|---|---|
| 不支持表格结构化提取 | PDF 表格会被当成连续文本，行列关系丢失 | 引入 `pdfplumber` 或表格识别模型，转成 Markdown 表格 |
| 不支持图片/图表内容 | 图片里的信息完全丢失 | 多模态模型做图文描述后再索引 |
| 不支持增量更新 | 文档改一页要整份重传 | 按页/按段做 diff，只重算变化部分（embedding 缓存已为此铺路） |
| OCR 需要手动安装 | 扫描件无法自动处理 | 默认集成 RapidOCR（体积换体验） |
| 单机部署 | Chroma embedded 无法多实例共享 | 切 `CHROMA_MODE=http` + 独立 Chroma Server（compose 已备好） |
| 没有鉴权 | 无登录体系，靠 `user_id` 参数隔离 | 接入 JWT + RBAC，向量库过滤条件从 token 解析 |
| 没有引用去重排序展示 | 引用列表按召回顺序，未按页码排序 | 输出前按 (doc, page) 排序（成本极低，容易补） |
