## 一、文档解析层

### 难点 1：PDF 是"排版格式"不是"语义格式" 🔴

**现象**：直接提取文本后，页眉页脚混进正文，双栏论文左右栏交错读串行，
跨页的句子被硬切断。

**根因**：PDF 只描述"某个字符画在哪个坐标"，不描述阅读顺序。
`page.get_text()` 按内部对象顺序输出，不保证是人类阅读顺序。

**方案**（分层处理）：

1. **用坐标而不是纯文本**：`page.get_text("dict")` 拿到每个文本块的 bbox 坐标。
2. **双栏检测**：统计所有文本块的 x 中心点分布。如果呈现明显的双峰（左栏/右栏），
   则按 x 坐标分左右两组，各组内按 y 排序后再拼接。
3. **页眉页脚自动识别**：不写死"去掉前 50 像素"。改为**跨页重复检测** ——
   把每一页的首/尾几行文本收集起来，若某行文本出现在超过 50% 的页面上，
   判定为页眉/页脚并剔除。这个方法对论文、手册、规范都通用，不需要针对每份文档调参。
4. **断行合并**：中文行尾没有连字符，若上一行末尾不是句末标点（。！？：；），
   且下一行开头不是标题序号，则合并。

**如何验证**：准备 3 份典型 PDF（单栏论文、双栏论文、带页眉页脚的手册），
解析后打印前 20 个 chunk，人工检查语义是否连续。

**面试怎么讲**：

> "PDF 解析的核心矛盾是它没有阅读顺序信息。我用 PyMuPDF 拿文本块的坐标，
> 通过 x 坐标聚类判断单双栏，通过跨页重复行检测自动识别页眉页脚。
> 用重复检测而不是固定位置，是因为不同文档的页眉高度不一样，
> 写死位置的话每换一份文档就要重新调参。"

---

### 难点 2：扫描件是纯图片 🟡

**现象**：解析后文本为空或只有零星几个字符，但文件明明有几十页。

**根因**：扫描件/图片型 PDF 里没有文本层。

**方案**：解析后统计每页有效字符数，低于 `OCR_FALLBACK_THRESHOLD`（默认 80）
判定为扫描页，走 OCR 降级链路（PaddleOCR / RapidOCR）。
**关键是要给出明确提示**，而不是静默返回空结果 —— 用户上传完看到"就绪"却问不出东西，体验最差。

**设计取舍**：OCR 是重量级依赖（PaddleOCR 会拉入好几个 GB 的模型）。
本项目把它做成**可选依赖**：默认不装，检测到扫描件时抛出 `DOC_OCR_REQUIRED`
并提示用户安装。这样保持了主链路轻量。

**面试怎么讲**：

> "我没有在项目里默认集成 OCR，因为它会给所有用户增加 2GB 依赖，
> 但 90% 的电子版 PDF 用不上。我做成按需降级 + 明确报错，
> 这是工程上对依赖膨胀的取舍。"

## 二、分块层

### 难点 3：切太碎丢语义，切太大检索不准 🔴

**现象**：固定 500 字切分后，检索命中的片段是"半句话"，LLM 回答不完整；
把块调大到 1500 字后，检索精度又明显下降。

**根因**：**检索粒度和生成粒度的最优解不同**。检索要小（语义聚焦、向量不被稀释），
生成要大（上下文完整）。单层分块无法同时满足。

**方案**：**父子块（Small-to-Big）双层索引**。

```
父块 1500 字（按章节标题切）
 └─ 子块 300 字 × N  ← 只有子块进向量库
```

- 检索命中子块 → 拿到 `parent_id` → 回查父块全文
- 多个子块命中同一父块 → **去重合并**，只送一份父块给 LLM

**额外收益**：因为父块去重，实际送进 Prompt 的 token 反而比"直接塞 20 个 300 字块"
少且完整。这是一个"精度和成本同时改善"的方案，比较少见。

**如何验证**：评测集上对比三种策略的 Recall@5（见 `docs/05-评测方案.md`）。

**面试怎么讲**：

> "分块的核心洞见是：检索和生成需要不同的粒度，所以不能只切一层。
> 我把子块用于建索引保检索精度，父块用于喂模型保上下文完整，
> 中间用 parent_id 关联。而且因为父块去重，token 反而更省了。"

---

### 难点 4：中文按字符数切分会在词语中间断开 🟡

**现象**：一句话被从"设备维护周" / "期是三个月"之间切断。

**方案**：切分时按优先级找分隔符 —— `\n\n`（段落）→ `\n`（行）→ `。！？；`（句）→ `，、`（读）→ 字符。
这是 LangChain `RecursiveCharacterTextSplitter` 的思路，但中文的分隔符集必须换掉
（英文的 `. ` 在中文里没有意义）。

**补充一个细节**：切分后要丢弃长度小于 `MIN_CHUNK_SIZE` 的碎片（如单独一个页码"12"），
否则这些碎片也会被向量化，污染检索结果。

## 三、检索层

### 难点 5：向量检索对型号、数字、专有名词不敏感 🔴

**现象**：问「1333 机种钢刀的更换周期」，召回的全是"设备维护""刀具管理"相关但机种不对的段落。

**根因**：Embedding 模型把文本压成语义向量时会**丢失精确的词面信息**。
`1333` 和 `1335` 在语义空间里几乎一样近，但对业务来说是天壤之别。

**方案**：**混合检索** —— 向量召回 Top-20 + BM25 关键词召回 Top-20，用 RRF 融合。

- 向量负责"意思对"
- BM25 负责"词对"（型号、编号、专有名词、数字）

BM25 中文需要分词，用 `jieba`；且必须把型号类 token 加入自定义词典，
否则 `1333` 可能被切碎。

**如何验证**：构造 10 条**包含精确型号/数字**的问题，对比纯向量 vs 混合检索的命中率。
这类问题的差距会非常明显，是最有说服力的实验数据。

**面试怎么讲**：

> "纯向量检索的失败模式很典型：语义相近但事实不同的内容分不开。
> 我加了 BM25 一路做混合检索。这里有个坑 —— RRF 融合只用排名不用分数，
> 否则向量的余弦相似度和 BM25 的分数根本不在一个量纲上，归一化方式又是个新的调参坑。"

---

### 难点 6：RRF 的 k 参数怎么选 🔴

**公式**：$\text{RRF}(d) = \sum_i \frac{1}{k + \text{rank}_i(d)}$

**k 的作用**：`k` 越小，排名靠前的文档权重差异越极端；`k` 越大，各排名权重越平均。

- `k=0`：第 1 名权重 1.0，第 2 名 0.5，第 3 名 0.33 —— 头部过于极端
- `k=60`：第 1 名 0.0164，第 2 名 0.0161 —— 更平滑，且**抗单路噪声**

**为什么默认 60**：这是原论文的经验值，且在大多数场景下表现稳定。
工程上不建议在这个参数上花太多时间，**先调 chunk 大小和 rerank 收益更大**。

---

### 难点 7：召回率和延迟的权衡 🟡

**现象**：把 `TOP_K` 从 20 调到 100，召回率涨了，但响应时间从 2s 涨到 8s。

**根因**：Rerank 是 O(n) 次前向计算。召回 100 条就要跑 100 次交叉编码器。

**方案**：分层控制。

| 阶段 | 数量 | 手段 |
|---|---|---|
| 全量 → 候选 | 20 + 20 | 向量 + BM25，毫秒级 |
| 候选 → 精排 | 20（去重后） | RRF 融合，零成本 |
| 精排 → 入 Prompt | 5 | Cross-Encoder，300ms 级 |

**面试怎么讲**：

> "召回和精排是一对取舍：召回要快要宽，精排要准要窄。
> 我的配置是 20+20 召回、融合后精排、取 Top-5 进 Prompt。
> 如果要再提召回率，我会优先改 chunk 策略和 embedding 模型，
> 而不是无脑加大 Top-K —— 后者边际收益递减，延迟是线性增长的。"

## 四、生成层

### 难点 8：LLM 幻觉 —— 文档里没有的也能编 🔴

**现象**：问文档里没写的内容，模型依然给出一个看起来很专业的答案。

**根因**：LLM 的训练目标是"生成通顺的回答"，不是"承认不知道"。
单纯在 Prompt 里写"不知道就说不知道"只能缓解，不能根治。

**方案**：**四道防线**，层层收紧。

| 防线 | 手段 | 可靠性 |
|---|---|---|
| 1. 检索侧 | 精排最高分 < 阈值 → 直接拒答，**根本不调用 LLM** | 高 |
| 2. Prompt 侧 | 明确约束"仅依据片段回答" + 少量示例 | 中 |
| 3. 结构侧 | 要求逐句标注 `[编号]`，编号对应上下文 | 中 |
| 4. **服务端校验** | 解析答案里的引用编号，**校验编号是否真实存在于上下文**，不存在的引用剥离或整段拒答 | 高 |

**关键认识**：防线 1 和 4 是**代码层面的硬约束**，不依赖模型"听话"。
面试时这一点很重要 —— 说"我靠 Prompt 防幻觉"是初级答案，
说"我知道 Prompt 不可靠，所以在代码层做了校验"才是工程答案。

**如何验证**：评测集里放 10 条**文档中不存在答案**的问题，统计拒答率。
理想情况下拒答率应接近 100%，误答率接近 0。

---

### 难点 9：Token 爆炸与 Lost in the Middle 🟡

**现象**：塞 20 个块进 Prompt，token 上万，又贵又慢；而且模型对**中间位置的上下文**
注意力明显下降，容易忽略关键信息。

**根因**：两个独立问题叠加 —— 上下文长度成本是线性的，但模型对长上下文的利用是非均匀的。

**方案**：

1. **父子块去重** —— 20 个子块可能只对应 4 个父块，token 直接降一个数量级
2. **精排截断** —— 只取 Top-5
3. **顺序编排** —— 把精排分数最高的放在**最前和最后**，次高的放中间（对抗 Lost-in-the-Middle）
4. **上下文压缩**（可选）—— 超长时先用小模型对每个片段做摘要再拼

**面试怎么讲**：

> "很多人只盯着'怎么塞更多上下文'，但长上下文有边际递减甚至负收益 ——
> 这就是 Lost in the Middle。我的做法是先把上下文量降下来（父子块去重 + 精排截断），
> 再考虑顺序编排，把最相关的放头尾。"

## 五、并发与工程化

### 难点 10：大文件解析阻塞请求 🟡

**现象**：上传 50MB 扫描版 PDF，接口转圈 2 分钟，被网关 504 掐断。

**方案**：异步任务流水线。

- 上传接口只做**校验 + 落盘 + 投递队列**，立即返回 `202 + task_id`
- 前端轮询 `GET /documents/{id}` 拿状态
- 任务表用**状态机**：`PENDING → PARSING → EMBEDDING → READY / FAILED`

**为什么不用 `ready` 布尔值**：长事务中间失败时，布尔值无法告诉你失败在哪一步，
重试就只能整份重跑。状态机让重试可以精确到阶段。

**面试怎么讲**：

> "这里其实和我之前做数据同步遇到的问题同构 —— 长链路任务必须有状态机，
> 否则失败重试的粒度太粗。我把解析拆成解析/清洗/分块/向量化四个可观测阶段，
> 每步都落库，失败能定位到具体阶段。"

---

### 难点 11：重复上传产生重复向量 🟡

**现象**：用户网络卡了点了两次上传，向量库里同一份文档存了两遍，检索结果里出现重复引用。

**方案**：**内容 MD5 作为幂等键**。

- 上传时先算文件 MD5，查库
- 已存在且 `READY` → 直接返回已有 `doc_id`（秒传）
- 已存在但处理中 → 返回已有任务状态，不重复投递
- 已存在但 `FAILED` → 复用原记录并重试

**注意**：文件级 MD5 不够 —— **用户改了文件名重新上传，MD5 不变，应该判定为同一份**；
反之，同一份文件改了内容，MD5 变了，应该判定为新文档。用内容 hash 而不是文件名，正是这个原因。

---

### 难点 12：删除文档后检索到"幽灵数据" 🟡

**现象**：删除了文档，向量库里的 chunk 还在，检索时还能召回出来。

**根因**：向量库和关系库是两个独立的存储，没有跨库事务。

**方案**：**三段式删除**。

```
① 关系库标记 status=DELETED（立即对用户不可见，秒级生效）
② 异步清理向量库中该 doc_id 的所有 chunk
③ 可选：清理原文件 + 硬删记录
```

**兜底**：检索时**强制过滤 `doc_id in (有效文档列表)`**。
即使清理任务失败了，也不会检索到已删内容 —— 用查询过滤做最终一致性保护。

**面试怎么讲**：

> "跨存储的删除没有事务可用，所以我用了'先软删再异步清理'，
> 并且在检索侧加了兜底过滤。宁可短暂不可见，也不能检索到已删内容 ——
> 这是业务上唯一可接受的方向。"

---

### 难点 13：多用户数据隔离 🟡

**现象**：A 用户提问，检索到了 B 用户的文档片段。

**方案**：`user_id` 写进**向量库的元数据**，检索时**带上 where 过滤条件**。

```python
collection.query(
    query_embeddings=[vec],
    where={"user_id": {"$eq": user_id}},   # ← 必须下沉到向量库
    n_results=20,
)
```

**为什么不能在应用层过滤**：向量库先召回 Top-20，应用层再过滤掉别人的，
如果你的文档占了绝大多数，Top-20 可能被过滤到只剩 1 条 —— 召回质量崩塌。
**过滤条件下沉到向量库，是在候选生成阶段就排除，而不是事后筛。**

这是一个很容易被忽略、但面试官很爱问的点。

---

### 难点 14：Embedding 重复计算浪费成本 🟡

**现象**：同一份文档被重复处理、或多用户上传相同模板文档，每次都重新算一遍 embedding。

**方案**：**内容 hash 缓存**。

- `chunk.content` 的 SHA256 作为 key，查 Redis / 本地缓存拿向量
- 命中则直接复用，未命中才调用模型

**收益**：文档更新场景下（改了一页重新上传），只有变化的 chunk 需要重算。
100 页文档改 1 页，embedding 计算量从 100% 降到 ~1%。

---

### 难点 15：本地模型的冷启动开销 🟡

**现象**：服务启动后第一个问答请求要等 30 秒。

**根因**：`SentenceTransformer` 首次加载要从磁盘读模型权重并初始化计算图。

**方案**：

1. 在 FastAPI 的 `lifespan` 启动钩子里**预热**（加载模型 + 跑一次 dummy 推理）
2. 模型对象做**进程级单例**（用 `lru_cache` 装饰工厂函数）
3. 推理加 `torch.inference_mode()` 关闭梯度计算，省显存和时间
4. 容器部署时**模型目录挂载成 volume**，避免每次重建镜像重新下载 2GB

**面试怎么讲**：

> "本地模型是进程级单例 + 启动预热。如果不预热，第一个用户会等 30 秒，
> 这在生产上是不可接受的。另外容器里我把模型缓存目录挂成了 volume，
> 多个副本共享同一份权重。"

---

## 六、效果度量

### 难点 16：改完不知道有没有变好 🔴（方案已定，数据待产出）

**现象**：调完 Prompt "感觉好像好一点"，但说不出具体提升。面试被问"你怎么衡量效果"直接卡住。

**根因**：RAG 是**多阶段链路**，最终答案的好坏无法定位到具体环节。

**方案**：**分层评测 + Golden Set**。

先建 40 条评测样本，每条包含：`问题` + `标准答案` + `应命中的 chunk id`。

| 层级 | 指标 | 衡量什么 |
|---|---|---|
| 检索层 | Recall@K | 该召回的 chunk 有没有进候选集 |
| 检索层 | MRR | 正确的 chunk 排得够不够前 |
| 生成层 | Faithfulness（忠实度） | 答案是否完全由上下文支撑，有无编造 |
| 生成层 | Answer Relevancy | 答案是否切题 |
| 生成层 | Context Precision | 送进 Prompt 的上下文里有多少是真有用的 |
| 工程层 | 首 token 延迟 P95 / 总耗时 | 用户体验 |
| 工程层 | 单次问答 token 成本 | 钱 |

**关键认识**：**检索指标必须单独测**。因为答案不好时，你无法区分是"没检索到"
还是"检索到了但 LLM 没用对"。分层评测就是为了把问题定位到环节。

**面试怎么讲**（这是拉开差距的地方）：

> "大部分 RAG demo 的问题是没有评测。我建了一套 40 条 Golden Set，
> 把指标拆成检索层和生成层。因为我发现只看最终答案准确率没法定位问题 ——
> 答案错可能是召回没召到，也可能是召回了 LLM 没用对，
> 这两种情况的优化方向完全相反。"

---

### 难点 17：评测集从哪来 ⚪

**方案**（三条路径，按成本排序）：

1. **从真实使用中沉淀**：问答接口加点踩反馈，点踩的问题人工标注后进评测集。
   这是最真实的来源，但需要时间积累。
2. **LLM 辅助生成**：把文档分块喂给 LLM，让它生成"这个块能回答的问题"。
   生成快，质量需要人工复核。**注意要包含一部分"文档中无答案"的问题**，用来测拒答能力。
3. **人工构造**：针对关键业务场景手写 10~20 条。量少但质量最高。

**当前项目采用**：2 + 3 结合，生成后用人工筛选。评测集放在 `eval/golden_set.jsonl`。

## 九、P1 实战记录：真实文档暴露出来的问题

上面第一~八节是**设计阶段识别**的难点。这一节记录的是 P1 阶段用真实 PDF
跑通链路后**实际踩到**的问题 —— 这些比纸面分析更有说服力，
因为每个都有"现象 → 定位过程 → 修复 → 验证"的完整闭环。

测试样本：一份 2 页的真实简历 PDF（`张煜科-应届生年经验-全栈开发实习生.pdf`）。

### 9.1 标题识别阈值：1.15 倍比率在这份文档上完全失效 🔴

**现象**：解析出的 7 个章节标题（教育背景、技能特长、实习经历……）**一个都没识别出来**，
反而把简历顶部的表单项标签块（`年　　龄 / 22 岁 / 性　　别 / 男`）误判成了标题。

**定位过程**：

第一步先 dump 字号分布，结果很意外：

```
字号分布(按块数)
    9.4  x66      ← 正文
    9.9  x12
   10.4  x6       ← 真标题就在这里
   13.1  x3       ← 被误判的图标标签块
   18.9  x1       ← 姓名
```

真标题是 **10.4pt**，正文 **9.4pt** —— 只大 **1pt**，比率 **1.106**，
而我的阈值是 **1.15 倍**，正好卡在下面。

第二步看字体名想找更强的信号，结果发现这份 PDF 用 **Type3 字体**（中文逐字嵌入），
字体名是 `Type3 (179 0 R)` 这种无意义的对象引用，粗体标志也全是 0。
**字体名和 bold 标志这两条常见路子在这类 PDF 上完全不可用。**

**根因**：用**纯比率**判定字号层级，在小字号文档上不成立。
PDF 里标题与正文的字号差往往是一个**绝对量**（0.5~1.5pt），
而不是一个比例 —— 正文 9.4pt 时，标题 10.4pt 也只差 1pt。

**修复**（三处）：

1. **改用绝对差 + 比率取较大值**：
   ```python
   delta = max(0.8, body_font_size * 0.06)
   font_heading = block.font_size >= body_font_size + delta
   ```
   正文 9.4pt 时阈值为 10.2pt → 10.4 命中；9.9 的日期行被正确排除。

2. **正文字号改用众数（按字符数加权）而不是中位数**：
   均值/中位数会被少量大标题拉高，导致"真标题反而显得不够大"。
   众数天然锁定"出现最多的那个字号"，而正文在字符数上必然占绝对多数。

3. **标题必须是单行**（硬性规则）：
   这一条直接干掉了那个 13.1pt 的误判 —— `年　　龄\n22 岁\n性　　别\n男`
   是表单标签块被 PyMuPDF 合并成一个块，字号偏大但是多行。
   **真实文档里的标题一定是单行**，这是比字号更强的约束。

**验证结果**：标题数从「4 个（2 个是垃圾）」变成「7 个（全部正确）」；
最短子块从 13 字提升到 31 字。

> **面试怎么讲**：
> "我用一份真实简历测解析链路，发现 7 个章节标题一个都没识别出来。
> 定位后发现两个问题叠加：一是我的字号阈值用的是比率（1.15 倍），
> 但真实文档里标题只比正文大 1pt，比率才 1.1；
> 二是那份 PDF 用 Type3 字体，字体名和粗体标志全都不可用，
> 常规的'看字体名判断粗体'的路子走不通。
> 最后我改成了绝对差 + 比率取较大值，并加了一条硬性规则：标题必须是单行 ——
> 因为真实文档里标题一定是单行，而多行大字号块基本都是表格或表单标签。
> 这一条把误判直接清零了。"

### 9.2 图标字体的私用区码点污染文本 🔴

**现象**：清洗后的正文里混着 `\ue621`、`\ue61f`、`\ue629` 这类字符，
在终端里显示成方块，并且会被送进 embedding。

**根因**：简历里的小图标（电话、邮箱、性别）用了 `iconfont` 字体，
在 PDF 文本层留下 Unicode **私用区（PUA，U+E000–U+F8FF）** 的码点。
这些码点没有语言学含义，只是图标字形的索引。

**修复**：在清洗阶段用正则剥掉私用区字符。

```python
_PUA_RE = re.compile(r"[\ue000-\uf8ff\U000f0000-\U000ffffd]")
```

**代价（要主动说明）**：极少数把生僻汉字映射进私用区的字体会被一并删掉。
权衡下来，去图标噪音的收益远大于偶发丢一个生僻字。

> 这是一个典型的"**清理策略必须有明确取舍**"的例子。
> 面试时把代价说出来，比声称"完美解决"可信得多。

### 9.3 复用已删除记录时漏了文件搬运（真实 bug）🔴

**现象**：测试用例 `test_reupload_after_delete_is_reprocessed` 失败 ——
删除文档后重新上传同一份文件，状态直接变成 `FAILED`。

**根因**：幂等分支写漏了一行。

```python
# 有 bug 的版本
if existing.status == DocumentStatus.DELETED.value:
    await _reuse_deleted(session, existing, final_path, filename, size)
    _safe_unlink(tmp_path)   # ← 临时文件被删了
    return existing, True
```

`_reuse_deleted` 把 `file_path` 设成了 `final_path`，但**从来没有人把临时文件搬到那里**；
而 `final_path` 在之前的删除操作里已经被清掉了。后面解析时读到不存在的文件，直接失败。

**修复**：复用已删除记录时，先把临时文件搬到最终路径。

```python
await asyncio.to_thread(os.replace, tmp_path, final_path)
await _reuse_deleted(session, existing, final_path, filename, size)
return existing, True
```

**这个 bug 的教训**：幂等分支有 4 条路径（已删除 / 失败 / 处理中 / 已就绪），
每条对临时文件的处理都不一样（搬走 / 保留 / 删除）。
**多分支的资源生命周期管理是最容易出错的地方**，必须为每条分支都写测试。

> **面试怎么讲**：
> "我在幂等上传的四个分支里漏了一条 —— 复用已删除记录时忘了把临时文件搬到最终路径。
> 这个 bug 单测直接暴露了，因为删除操作会清掉原文件。
> 它让我意识到多分支的资源生命周期管理必须逐条写用例，
> 因为每条分支对临时文件的处理都不同，靠肉眼 review 很容易漏。"

### 9.4 aiosqlite 的 DEBUG 日志淹没业务日志 🔴

**现象**：开启 `DOCMIND_DEBUG=true` 后，一次文档入库产生了**上千行日志** ——
全是 `executing functools.partial(<built-in method execute of sqlite3.Cursor object at 0x...>, 'INSERT INTO ...')`
这类 SQL 和游标操作日志，自己的业务日志完全找不到。

**根因**：日志级别设成 DEBUG 后，根 logger 是 DEBUG，
`aiosqlite` 和 `sqlalchemy.engine` 也跟着输出 DEBUG 级别的日志。
而它们会把**每一条 SQL 和每一个游标操作**都打出来。

**修复**：加入降噪名单。

```python
for noisy in (..., "aiosqlite", "sqlalchemy.engine", "sqlalchemy.pool"):
    logging.getLogger(noisy).setLevel(logging.WARNING)
```

**为什么值得单独记一笔**：这不是"配置问题"，而是**可观测性设计问题**。
日志的目的是"让我看到我想看的东西"，噪音和缺失同样是缺陷。
排查 ORM 问题时可以临时把这两个名字从名单里去掉，但不应该长期开着。

> **面试怎么讲**：
> "我把日志级别开到 DEBUG 调试时，一次入库产生上千行 SQL 日志，
> 完全找不到自己的业务日志。我意识到这是可观测性的设计问题 ——
> 日志的价值在于信噪比，不是数量。所以我在日志初始化里做了第三方库降噪。"

## 十、语音模块实战记录：三个 bug 都是"只有真跑才会暴露"的类型

语音模块上线后接连撞到三个问题。它们的共同点是：**桩测试全绿、代码 review 也看不出来**，
每一个都需要"真实调用 + 真实用户环境"才会现形。这一节按发现顺序记录。

### 10.1 Windows 上 NamedTemporaryFile 的独占句柄 🔴

**现象**：用户第一次用语音输入就失败：

```
语音识别失败: 语音识别调用失败:
[Errno 13] Permission denied: 'C:\Users\...\AppData\Local\Temp\tmpq5y532d0.wav'
```

**定位过程**：先写了个最小复现脚本对比三种写法：

| 写法 | Windows 上再开一个句柄 |
|---|---|
| `NamedTemporaryFile` 保持打开 | ✗ `PermissionError` |
| 先 `close()` 再开 | ✓ |
| `TemporaryDirectory` + 手动写 | ✓ |

**根因**：`NamedTemporaryFile` 在 Windows 上以**独占方式**打开文件
（`CreateFile` 不带 `FILE_SHARE_READ`）。而 DashScope SDK 内部会自己
`open(file, "rb")` 去读音频（这一点后来在
`dashscope/audio/asr/recognition.py` 的 `Recognition.call` 源码里得到确认），
于是被系统拒绝。

**POSIX 允许同一路径被多个句柄打开，所以这个 bug 只在 Windows 上出现** ——
在 Linux 上开发永远碰不到，测试也照样绿。这是最危险的一类平台差异。

**修复**：换成 `TemporaryDirectory` + 手动写文件，**先把句柄关掉**再把路径交给 SDK。

```python
with TemporaryDirectory(ignore_cleanup_errors=True) as tmpdir:
    path = Path(tmpdir) / f"audio{suffix}"
    path.write_bytes(audio)          # 句柄随 write_bytes 关闭
    sentences = await asyncio.to_thread(self._recognize_sync, str(path))
```

**回归测试的平台差异必须写清楚**：测试用"独立句柄重新读一次文件"来断言，
但**这条断言在 Linux 上即使代码退化成旧 bug 也会通过**。
它真正起作用的地方是 Windows（CI 里有 `windows-latest`）。
不写清楚的话，后人看到 Linux 全绿会以为这条防线没用。

> **面试怎么讲**：
> "语音输入一上线就报 Permission denied。定位下来是 Windows 的
> `NamedTemporaryFile` 会独占文件，而 SDK 内部要自己再打开一次 ——
> POSIX 允许共享，所以这个坑在 Linux 上根本复现不出来。
> 我写了三种写法的最小对比脚本确认，换成 `TemporaryDirectory` 后解决。
> 这件事让我在写回归测试时特意标注了'这条断言在 Linux 上是空转的'，
> 因为不写清楚的话，后面的人会误判这条测试没价值。"

### 10.2 采样率：配置值 vs 文件真实值 🔴

**现象**：修完上个问题后，往返验证脚本立刻报：

```
语音识别失败(44): Failed to decode audio:
sample rate 16000 not equals with real 24000
```

**根因**：`settings.speech_asr_sample_rate = 16000` 是给**浏览器录音（WAV）**用的，
但 edge-tts 合成出来的是 **24kHz MP3**。我把配置值无条件传给了 SDK，
而 Paraformer 会校验"声明值"和"文件头里的真实值"是否一致。

**修复**：加一个**零依赖的音频头解析器**（`services/speech/audio_probe.py`）：

- **WAV**：采样率在偏移 24，4 字节小端
- **MP3**：第一个帧头的第 10~11 位是采样率索引（**必须先跳过开头的 ID3 标签**，
  否则读到的是 `ID3\x03` 而不是帧同步字）

读不出来的格式（m4a/opus/aac）返回 `None`，调用方退回配置值 ——
**宁可退回也不要猜**，猜错得到的是乱码而不是报错。

**为什么不引库**：读采样率只要看几十个字节的头，为这点事引入
`soundfile` / `ffmpeg` 不划算 —— 尤其 ffmpeg 是个 70MB 的外部二进制，
和项目"零安装"的主张冲突（这也是前端不用 MediaRecorder 的同一个理由）。

**顺带修掉的同类问题**：`format="wav"` 原本是写死的，但接口层允许上传 mp3。
把 mp3 声明成 wav **不会报错，只会识别出乱码** —— 和采样率是同一类
"声明与实物不符"的坑，所以一并改成了按后缀映射。

**过程中测试还抓到了我自己代码的一个 off-by-one**：`range(limit - 4)`
在 4 字节输入时循环体一次都不执行，且永远扫不到紧贴末尾的同步字。
写 MP3 帧头解析时这种边界极容易错。

### 10.3 误解了 SDK 契约：结果不走回调，走返回值 🔴

**现象**：采样率修好后，**识别结果永远是空字符串**，但 `status_code` 是 200、
耗时也正常（1.1 秒）。看起来像"用户没说话"。

**定位过程**：直接读 SDK 源码（`inspect.getsource`），发现两件事：

1. `Recognition.call()` **全程不调用我们传入的回调** ——
   它自己在内部循环里收集 `sentences`，然后 `return RecognitionResult(response, sentences, usages)`
2. `RecognitionResult.get_sentence()` 的返回类型是 **union**：
   - 有完整分句时 → 返回 **`list[dict]`**
   - 只有一个不完整结果时 → 返回 **`dict`**

我原来的实现把 `on_event` 当主要来源，只处理了 `dict` 分支 ——
**两条都错**，所以正常识别出内容时反而拿到空串。

**修复**：结果只从返回值取，并且两个分支都处理：

```python
payload = result.get_sentence()
if isinstance(payload, list):
    return [item["text"] for item in payload if isinstance(item, dict) and item.get("text")]
if isinstance(payload, dict) and payload.get("text"):
    return [payload["text"]]
return []
```

**这条的教训最值得说**：

> **mock 只能验证"我以为的契约"，验证不了契约本身对不对。**

我那 30 个桩测试全绿 —— 因为桩是我按自己的理解写的，**它和我的理解一样错**。
必须有一次真实调用才能发现。所以最后单独写了
`backend/scripts/verify_speech_roundtrip.py`：用 edge-tts 说一句话，
再让 Paraformer 听回来，**全程自动且判定客观**（合成时知道原文，识别回来一比对）。

**修复后的往返验证结果**：

```
原文: 我在项目里用 Redis 做了缓存，把订单查询的响应时间降低了百分之四十。
识别: 我在项目里用read做了缓存，把订单查询的响应时间降低了40%。
```

字符重合度 74%，语义完全保留。但**「Redis」被听成了「read」** ——
这恰好是面试场景最要命的地方：候选人说的技术名词被识别错，会直接影响
后续追问的依据。

> 这是一个**尚未解决的已知问题**，也是下一步的优化方向：
> Paraformer 支持**热词（vocabulary）**，而简历里本来就有一份技术名词表，
> 可以把它作为热词喂给 ASR —— 用文档去提升识别率，和项目里
> "用文档驱动 RAG"是同一个思路。

### 10.4 附带发现：独立脚本读不到界面配置 🔴

**现象**：用户在界面上配好了百炼 Key，服务端 `/speech/status` 显示可用，
但冒烟脚本 `smoke_speech.py` 报"未配置阿里云百炼 Key"。

**根因**：`data/runtime_settings.json` 只在**应用启动时**被加载
（`main.py` 的 lifespan 调用 `load_runtime_overrides()`）。
所有直接调 service 层的独立脚本都读不到它，只能拿到 `.env` 与代码默认值。

**影响范围**：`parse_pdf.py` / `bench_large_pdf.py` 会用默认分块参数而不是界面调的；
`check_env.py` 会误报"未配置 LLM Key"。

**为什么这个 bug 值得单独记**：**工具给出误导性结论比不报还糟** ——
它会让人去查一个根本不存在的问题。我当时就差点顺着"Key 没配"这条线查下去。

**修复**：抽出 `backend/scripts/_common.py`，让所有脚本走
**和服务器完全一样的加载路径**：

```python
bootstrap()   # 加 sys.path + load_runtime_overrides(), 必须在 import app.* 之前
```

**关键约束**：必须在导入任何 `app.*` 模块**之前**调用 ——
配置对象在模块导入时就实例化了，晚一步就晚了。
（和 `conftest.py` 里反复强调的是同一个顺序问题。）

---

### 10.5 一句话总结这一节

三个 bug 的类型完全不同，但**都指向同一个方法论**：

| bug | 为什么单测发现不了 |
|---|---|
| Windows 独占句柄 | **平台差异** —— Linux 上行为合法 |
| 采样率不一致 | **依赖真实数据** —— 桩不产生真实音频头 |
| SDK 契约理解错 | **mock 和我的理解一样错** —— 自己骗自己 |

所以这个项目的验证策略是分层的：

| 层 | 手段 | 覆盖什么 |
|---|---|---|
| 单元 | pytest + 桩 | 逻辑分支、边界、错误码 |
| **真实链路** | `smoke_*.py` / `verify_*.py` | **外部依赖的真实行为** |
| 平台 | CI 的 windows + ubuntu runner | 平台差异 |

**桩测试保证"我改的东西没坏"，真实链路测试保证"它真的能用" —— 两者不能互相替代。**
