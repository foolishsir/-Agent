# 开发路线图

> 分阶段交付，每个阶段都有**可独立验证的产出**。
> 原则：先跑通端到端最小闭环，再逐层加固，避免"写了 3000 行但一次都没跑起来"。

---

## 阶段总览

| 阶段 | 主题 | 核心产出 | 验收标准 | 难度 |
|---|---|---|---|---|
| **P0** | 项目骨架 | 配置/日志/异常/响应/健康检查/环境自检 | `pytest` 全绿，`/docs` 可访问 | ⭐ |
| **P1** | 文档入库链路 | PDF 解析 → 清洗 → 父子分块 → Embedding → Chroma | 上传 PDF 后能在 Chroma 里查到 chunk | ⭐⭐⭐ |
| **P2** | 问答链路 | 混合检索 → RRF → Rerank → 流式生成 → 引用溯源 | 能对上传的 PDF 提问并得到带引用的答案 | ⭐⭐⭐⭐ |
| **P3** | 多轮对话 | Query 改写、会话持久化 | 能连续追问"它呢""为什么" | ⭐⭐ |
| **P4** | 工程化加固 | 异步队列、幂等、缓存、删除一致性、用户隔离 | 大文件不阻塞、重复上传不重复入库 | ⭐⭐⭐ |
| **P5** | 评测体系 | Golden Set + 指标脚本 + 对比实验 | 产出可写进简历的量化数据 | ⭐⭐⭐⭐ |
| **P6** | 前端与文档 | Vue3 界面、README、架构图 | GitHub 可展示 | ⭐⭐ |
| **P7** | 简历与面试材料 | 简历文案、面试问答手册、演示脚本 | 面试可直接用 | ⭐ |

## P0 — 项目骨架 ✅

**目标**：把"工程质量"这件事在第一天就立住，而不是最后补。

**产出**

```
docmind/
├── backend/
│   ├── app/
│   │   ├── main.py                 应用工厂 + 生命周期 + 全局异常处理
│   │   ├── core/
│   │   │   ├── config.py           强类型配置中心
│   │   │   ├── logging.py          trace_id 全链路日志
│   │   │   ├── exceptions.py       异常体系 + 错误码
│   │   │   ├── response.py         统一响应外壳
│   │   │   └── middleware.py       链路 id + 访问日志
│   │   └── api/
│   │       ├── router.py           路由聚合
│   │       └── v1/health.py        存活/就绪探针
│   ├── tests/                      单元测试
│   ├── scripts/check_env.py        环境自检脚本
│   └── Dockerfile                  多阶段构建，CPU 版 torch
├── docs/                           架构 / 选型 / 踩坑 / 路线图
├── docker-compose.yml              chroma + redis + backend + worker
├── .env.example                    配置模板
├── pyproject.toml                  pytest / ruff / mypy 配置
└── run-backend.cmd                 Windows 一键启动
```

**这一阶段解决的工程问题**

| 问题 | 处理方式 |
|---|---|
| 配置散落在代码里 | pydantic-settings 强类型校验，写错启动即报错 |
| 出问题查不到日志 | trace_id 贯穿 HTTP 请求与后台任务 |
| 前端要为每个接口写错误处理 | 统一响应外壳 `{code, message, data, trace_id}` |
| 业务代码里到处 `raise HTTPException` | 业务异常与 HTTP 状态码解耦 |
| 别人 clone 下来跑不起来 | `check_env.py` 一次性体检全部环境问题 |
| 就绪探针形同虚设 | 真实探测 6 项依赖，逐项返回明细 |

**验收**：`python -m pytest` 全绿；`python backend/scripts/check_env.py` 输出体检报告。

## P1 — 文档入库链路

**目标**：打通"上传 PDF → 向量库里有数据"这条最长的链路。

**模块拆解**

```
services/
├── parser/
│   ├── base.py              Parser 协议（为后续支持 docx/md 留口子）
│   ├── pdf_parser.py        PyMuPDF：文本块 + 坐标 + 页码
│   └── cleaner.py           页眉页脚剔除、断行合并、空白归一化
├── chunking/
│   ├── base.py              Chunker 协议
│   └── parent_child.py      父子块切分（章节标题感知 + 递归 + 重叠）
├── embedding/
│   ├── base.py              EmbeddingProvider 协议
│   ├── local_bge.py         本地 SentenceTransformer（query/passage 分离）
│   └── cache.py             内容 hash 向量缓存
└── vectorstore/
    ├── base.py              VectorStore 协议
    └── chroma_store.py      Chroma 实现（含元数据过滤）
```

**接口**

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/documents` | 上传 PDF，返回 doc_id + 状态 |
| GET | `/api/v1/documents` | 分页列表，支持状态筛选 |
| GET | `/api/v1/documents/{id}` | 详情 + 处理进度 |
| DELETE | `/api/v1/documents/{id}` | 软删 + 异步清理向量 |

**数据模型**

```
documents     id, user_id, filename, file_md5, size, page_count,
              status, error_msg, chunk_count, created_at, updated_at
chunks        id, doc_id, parent_id, content, page_start, page_end,
              section_path, chunk_type(parent/child), token_count
sessions      id, user_id, title, created_at
messages      id, session_id, role, content, citations(JSON), created_at
feedbacks     id, message_id, rating, comment, created_at
```

**验收**：上传一份 20 页 PDF，能在 Chroma 里 `count()` 到子块数量，
且随机抽 3 个子块能回查到正确的父块与页码。

## P2 — 问答链路

**目标**：端到端能问答，且答案带引用。

```
services/
├── retrieval/
│   ├── vector_retriever.py   向量召回
│   ├── bm25_retriever.py     关键词召回（jieba 分词 + 自建倒排）
│   ├── fusion.py             RRF 融合
│   ├── reranker.py           Cross-Encoder 精排
│   └── pipeline.py           检索编排（含各阶段耗时打点）
├── llm/
│   ├── base.py               LLMProvider 协议（achat / astream）
│   └── openai_compatible.py  DeepSeek / 通义 / 硅基流动通用实现
├── prompt/
│   └── templates.py          Prompt 模板（生成 / 改写 / 摘要）
└── rag/
    ├── pipeline.py           完整问答编排
    └── citation.py           引用解析与**服务端编号校验**
```

**接口**：`POST /api/v1/chat` （SSE 流式）

**SSE 事件设计**

```
event: stage     data: {"stage":"retrieval","candidates":40,"cost_ms":85}
event: citation  data: [{"index":1,"doc":"手册.pdf","page":12,"snippet":"..."}]
event: token     data: {"text":"钢刀"}
event: done      data: {"total_ms":2340,"tokens":{"prompt":1820,"completion":156},"refused":false}
event: error     data: {"code":"LLM_TIMEOUT","message":"..."}
```

> 把 `stage` 作为独立事件推给前端，用户能看到"正在检索文档…"的进度，
> 而不是一个空白转圈。这也是调试期观察各阶段耗时的入口。

**验收**：上传 PDF 后提问，答案末尾有 `[1][2]` 引用，点击能定位到原文页码；
问文档中不存在的问题时返回拒答话术。

## P3 — 多轮对话

**目标**：解决代词指代漂移。

**关键设计**：**检索用改写后的 query，生成用原始历史**。

```
用户：文档里钢刀的寿命是多久？
助手：根据文档 [1]，钢刀寿命为 20000 次或 3 个月。
用户：那锡膏呢？                    ← 直接检索必然跑偏
      ↓ Query 改写
      "文档里锡膏的寿命/使用期限是多久？"  ← 检索用这个
```

改写用一次轻量 LLM 调用（低 temperature，短 max_tokens）。
**优化点**：判断是否需要改写 —— 如果当前问题已经自包含（无代词、无省略），
跳过改写直接检索，省一次调用。这个判断可以用简单的规则匹配（含"它/这个/那/呢"等触发词）。

## P4 — 工程化加固

| 项 | 实现 |
|---|---|
| 异步任务 | RQ + Redis，`TASK_MODE=queue` 切换 |
| 幂等上传 | 文件 MD5 查重，命中直接复用 |
| 向量缓存 | chunk 内容 SHA256 → Redis 缓存向量 |
| 删除一致性 | 软删标记 → 异步清向量 → 检索侧兜底过滤 |
| 用户隔离 | `user_id` 下沉到 Chroma `where` 过滤 |
| 失败重试 | 任务状态机 + `tenacity` 指数退避 |
| 限流 | 按用户维度的问答 QPS 限制（防 token 被刷） |

## P5 — 评测体系

**Golden Set 格式**（`eval/golden_set.jsonl`）

```jsonl
{"id":"q001","question":"1333 机种钢刀的更换周期是多久？","answer":"20000 次或 3 个月","relevant_chunk_ids":["doc1_c012"],"category":"exact_match","doc_ids":["doc1"]}
{"id":"q002","question":"文档里有没有提到预算金额？","answer":"未提及","relevant_chunk_ids":[],"category":"no_answer","doc_ids":["doc1"]}
```

`category` 的分类很关键，因为**不同类别要分开看指标**：

| category | 测什么 |
|---|---|
| `exact_match` | 含型号/数字的精确匹配，测 BM25 那一路的价值 |
| `semantic` | 纯语义理解，测向量那一路的价值 |
| `multi_hop` | 需要跨段/跨页整合 |
| `no_answer` | **文档中无答案，测拒答能力** ← 最容易被忽略 |
| `multi_turn` | 代词指代，测 Query 改写 |

**指标脚本**（`eval/run_eval.py`）输出对比表：

```
策略对比 (n=40)
┌──────────────────────┬───────────┬────────┬──────────┬──────────┐
│ 策略                  │ Recall@5  │ MRR    │ 忠实度    │ 拒答准确率│
├──────────────────────┼───────────┼────────┼──────────┼──────────┤
│ 纯向量                │  0.xx     │ 0.xx   │  0.xx    │   -      │
│ 向量 + BM25 (RRF)     │  0.xx     │ 0.xx   │  0.xx    │   -      │
│ + Rerank              │  0.xx     │ 0.xx   │  0.xx    │   -      │
│ + 父子块              │  0.xx     │ 0.xx   │  0.xx    │   -      │
│ + 拒答阈值            │  0.xx     │ 0.xx   │  0.xx    │  0.xx    │
└──────────────────────┴───────────┴────────┴──────────┴──────────┘
```

> ⚠️ **诚实原则**：表里的数字必须是你自己跑出来的真实值。
> 简历上写"Recall@5 从 0.62 提升到 0.85"和写"大幅提升"是两种可信度。
> 而编造的数字一旦被追问细节就会崩。这张表是 P5 阶段最重要的产出。
