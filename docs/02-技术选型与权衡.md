# 技术选型与权衡记录

> 记录"为什么选它、为什么不选另一个、代价是什么"。
> 面试官判断一个项目是否真实，往往就看候选人能否说出**被放弃的方案和放弃的理由**。

## 1. 后端框架：FastAPI

| 维度 | FastAPI | Spring Boot | Flask |
|---|---|---|---|
| 异步原生 | ✅ async/await 一等公民 | ✅ WebFlux 但生态偏向阻塞 | ❌ 需 gevent 打补丁 |
| SSE 流式 | ✅ 原生 StreamingResponse | ✅ SseEmitter | ⚠️ 需额外配置 |
| RAG 生态 | ✅ 几乎所有库都是 Python | ❌ Spring AI 仍不成熟 | ⚠️ 需自己拼 |
| 类型校验 | ✅ Pydantic，请求/响应自动文档化 | ✅ Bean Validation | ❌ 无 |

**选择理由**：这个项目的瓶颈在"LLM 与向量模型生态"，而不在并发框架。
选 FastAPI 能把精力花在 RAG 链路上，而不是给 Java 找向量库客户端。

**代价**：团队如果是 Java 技术栈，运维体系（Nacos/Sentinel/Actuator）需要重新建。
如果是生产落地，我会选 **FastAPI 做 AI 能力层，Spring Boot 做业务网关**，通过 HTTP 内网调用。

## 2. 向量数据库：Chroma（embedded）

| 维度 | Chroma | Milvus | pgvector | FAISS |
|---|---|---|---|---|
| 部署成本 | ✅ pip 装完即用 | ❌ 需 Docker + etcd + MinIO | ⚠️ 需 PostgreSQL + 扩展 | ✅ 库级 |
| 元数据过滤 | ✅ 原生支持 | ✅ | ✅ SQL 表达力最强 | ❌ 不支持 |
| 增删改 | ✅ | ✅ | ✅ | ❌ 需自己管理 id 映射 |
| 水平扩展 | ❌ | ✅ | ⚠️ 需 Citus/分片 | ❌ |
| 适用量级 | 10 万级 | 亿级 | 千万级 | 百万级（只读） |

**选择理由**：Chroma 原生支持**带元数据过滤的向量检索**，这对多用户隔离是刚需；
FAISS 虽然快但纯库、不支持删除和过滤，做业务系统会很痛苦。

**关键取舍**：Chroma 的 embedded 模式把索引放在**应用进程内**，好处是零部署成本、无网络往返，
代价是**无法多实例共享**（两个进程各持一份索引，写入不互通）。

**因此代码里做了 `VectorStore` 抽象接口**，通过 `DOCMIND_CHROMA_MODE` 在
embedded / http 之间切换，数据量或部署形态变化时不需要改业务代码 ——
`docker-compose.yml` 里已经备好了 Chroma Server 服务。

**关于索引参数**：Chroma 底层是 HNSW。HNSW 的核心参数：

- `M`：每个节点的邻居数。调大 → 召回率高、内存涨、构建慢。默认 16。
- `ef_construction`：建索引时的候选队列长度。调大 → 索引质量高、构建慢。
- `ef_search`：查询时的候选队列长度。**这是唯一可以在线调的参数**，调大 → 召回率高、延迟涨。
- `space`：距离度量。文本用 `cosine`。

工程结论：**不要在 `M` 和 `ef_construction` 上过度调优**（要重建索引），
优先调 `ef_search` 做延迟/召回的在线权衡。数据量低于 1 万时 HNSW 相对暴力检索优势不明显，
Chroma 内部会按 `hnsw:construction_ef` 等阈值自动切换策略。

## 3. Embedding 模型：BAAI/bge-small-zh-v1.5（本地）

| 模型 | 维度 | 体积 | 中文效果 | 说明 |
|---|---|---|---|---|
| bge-small-zh-v1.5 | 512 | ~95MB | 良好 | **本项目选用**，CPU 可跑，下载快 |
| bge-base-zh-v1.5 | 768 | ~400MB | 更好 | 效果更优，成本可接受时推荐 |
| bge-m3 | 1024 | ~2.2GB | 最好 | 支持多语言 + 长文本，但太重 |
| text-embedding-3-small | 1536 | API | 好 | 需联网付费，数据出域 |

**选择理由**：小模型先跑通链路，验证效果后再换。**Embedding 模型是整个 RAG 里最值得投入的一环** ——
检索不到，后面 Prompt 写得再好也没用。

### ⚠️ 最容易踩的坑：BGE 的 query 侧指令

BGE 中文系列在训练时对 **query 侧**加了一句指令前缀：

```
为这个句子生成表示以用于检索相关文章：
```

而 **passage 侧不加**。这是**非对称**的。

如果代码里对 query 和 document 用同一套编码逻辑（很多人会这么写），检索效果会明显下降，
而且**不会报错** —— 只是召回率悄悄变低，极难发现。

因此 `config.py` 里专门拆了两个字段，并在 `EmbeddingService` 里分别走
`encode_query()` 和 `encode_passage()` 两条路径。这是本项目最重要的"隐性正确性"细节之一。

> 补充：不是所有模型都这样。`bge-m3`、`text-embedding-3-*` 是对称的，不需要指令。
> 换模型时必须同步确认这一点。

## 4. Rerank 模型：BAAI/bge-reranker-base

Cross-Encoder 会对每对 (query, passage) 做一次完整前向计算。
20 个候选 × 一次前向 ≈ 100~300ms（CPU），换来的是精度的大幅提升。

**成本控制**：`RERANK_TOP_N` 和 `VECTOR_TOP_K/BM25_TOP_K` 是一组联动参数 ——
召回 20 条精排到 5 条，是延迟与精度权衡后的经验配置。召回给到 100 条，精排会变成瓶颈。

## 5. LLM：DeepSeek（OpenAI 兼容协议）

选它的三个理由：

1. **协议兼容**：`openai` SDK 只需改 `base_url`，代码不绑死厂商。
2. **中文与成本**：中文效果好，价格低，适合做多轮评测实验（评测要跑几十上百次调用）。
3. **支持流式**：SSE 打字机效果依赖 `stream=True`。

**抽象设计**：`services/llm/base.py` 定义 `LLMProvider` 协议（`achat` / `astream`），
`openai_compatible.py` 是唯一实现。换成通义、硅基流动、vLLM 自部署，
**只需要改 `.env` 里的 `base_url` 和 `model`**，代码零改动。

> 面试可讲：这就是"面向接口编程"在 AI 应用里的实际价值 —— 模型迭代太快，
> 把厂商绑死在业务代码里是技术债。

## 6. 分块策略：父子块（Small-to-Big）

对比过的三种主流方案：

| 方案 | 检索粒度 | 生成上下文 | 问题 |
|---|---|---|---|
| 固定长度切分 | 中 | 中 | 会把句子/表格切断，语义碎片化 |
| 递归字符切分 | 中 | 中 | 按分隔符优先级切，比固定长度好，但仍是单层 |
| 语义分块（Embedding 相似度突变点） | 好 | 中 | 效果提升有限，但**索引成本翻数倍**（每个句子都要算 embedding） |
| **父子块（本项目）** | **好** | **好** | 需要维护 parent_id 映射，检索后要多一次父块回查 |

**为什么不做语义分块**：投入产出比不划算。用标题结构 + 递归切分已经能拿到 80% 的收益，
剩下 20% 用 Rerank 补更划算。

## 7. 异步任务：RQ vs Celery vs BackgroundTasks

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| FastAPI BackgroundTasks | 零依赖 | 与 Web 进程同生命周期，重启即丢；无法重试；占 Web 进程 CPU | 本地开发兜底 |
| **RQ** | 基于 Redis，API 极简，`job.meta` 天然适合做进度上报 | 功能比 Celery 少 | **本项目** |
| Celery | 功能全、生态大 | 配置复杂，对本项目属于过度设计 | 大型多队列场景 |

**设计**：`DOCMIND_TASK_MODE=inline` 时任务同步执行（开发调试不需要装 Redis），
`queue` 时投递 RQ。**同一份 `services` 代码两种模式都能跑**，因为任务函数只是 service 的薄包装。

这是一个很实用的设计：**让"能不能跑起来"不依赖外部中间件**，
降低了别人 clone 你项目的门槛 —— GitHub 项目的 star 数和首次运行成功率强相关。

## 8. 数据库：SQLite（开发）→ MySQL/PostgreSQL（生产）

通过 `DOCMIND_DATABASE_URL` 切换，代码层用 SQLAlchemy 2.0 async 统一。
开发用 SQLite 免安装；生产换 MySQL 只需改 URL 和驱动。

**注意**：SQLite 的并发写能力弱，`task_mode=queue` + 多 Worker 时必须换 MySQL，
否则会出现 `database is locked`。这一点在 `.env.example` 里有注释提醒。
